# 业务插件化落地设计

日期：2026-10-22。本文定义后续实现边界，当前代码状态以 plugin-architecture.md 为准。现有三个叶插件证明启停、依赖、事件和洞察通道；项目、工时及财务业务还没有完成抽离。

## 1. 内核保留什么

内核保留公司与个人身份、项目稳定标识、授权检查、附件安全存取、审计链、幂等事务、不可变账本和 outbox。项目是全系统关联的稳定中心；工作包、合同、工时、核算方法和视图属于可变业务。内核不持有具体行业的收入计算、发票或成本分摊算法。

核算插件通过内核记账接口提交有来源的事件，内核独立检查租户、权限、期间、来源唯一性、平衡与冲销关系。插件停用后，历史账目、审计和来源摘要仍由内核读取；不能要求安装某个旧版插件才能解释已经形成的金额。

## 2. 模块目录与依赖

以下为目标目录；除表中现有三个叶插件，其余尚未实现为独立应用。

| 插件 | 拥有的数据与逻辑 | 依赖 |
| --- | --- | --- |
| delivery | 项目阶段策略、模板、工作包、任务依赖、里程碑、风险、验收 | 项目标识与内核 |
| time | 本人工时、周报、提交与审核、资源容量 | delivery |
| costing | 生效日费率、月度人工池、共享费用、取整组与分摊 | time、内核账本 |
| contracts | 客户/供应商、合同版本、合同明细、变更与计量约定 | 项目标识 |
| settlement | 履约结算、应收应付、核销与账龄 | contracts、内核账本 |
| cash | 现金流水、待匹配区、预收预付、退款、13周计划 | settlement、内核账本 |
| invoicing | 发票登记、明细分配、红冲与待确定税额 | settlement |
| management_revenue | 管理收入事件与调整，逐合同明细采用唯一方法 | contracts、delivery、time |
| insights | 经营口径、预算/EAC/毛利、现金预测与风险解释 | 对所需来源声明依赖；缺少来源显示未启用 |
| notifications | 站内待办、事件订阅、扫描、已读与去重 | outbox |

| project_health（现有） | 按已授权快照生成规则提醒 | 无 |
| delivery_watch（现有） | 七天内到期的里程碑提醒 | project_health |
| agent_gateway（现有） | 启停个人 API；当前路由与认证由 core 实现 | 无 |

一个插件的页面、API、表单、模型、迁移、服务、工具描述、规则、导入器与测试归同一目录所有。禁止因为新增一张业务表单就把逻辑继续堆进 core/views.py。跨插件不直接写表；依赖方调用版本化查询/命令接口或订阅事实事件。

## 3. 扩展点与契约

WO-14 首先实现以下扩展点；这不是对当前 API 的描述：

1. 注册：在部署时加载受信模块；版本与依赖静态检查通过后才成为可启用候选。不提供 Web 上传任意 Python 包。
2. 数据：每个 Django App 使用自己的 app label、表名前缀与迁移链。外键只指向稳定项目/公司标识及已声明的依赖；迁移禁止修改其他插件或内核的表。
3. 页面：只允许登记到命名空间中的固定路由；导航、HTTP 入口、导入器、定时任务、个人工具和服务命令统一检查启用状态。隐藏导航不能替代入口门控。
4. 查询：先生成已授权快照，再交给洞察或个人 Agent。财务汇总与个人费率采用不同接口，默认不暴露费率。
5. 命令：声明输入 schema、身份/项目范围、所需权限、幂等键和输出 schema；先调用内核 guard，再进入业务事务。插件不得获取共享管理员令牌。
6. 事件：业务和 outbox 同事务写入；topic 与 payload 都有版本。消费者用 event_id 去重，不以重试次数判断事实是否发生。跨版本重放需要显式转换器和反例测试。
7. 记账：金额为整数分，来源与算法版本持久化。不得由模型返回值直接触发过账，不允许插件更新历史账本行。

内核 API 兼容期内只做向后兼容增加。破坏性接口升级使用新主版本，插件版本和依赖范围同步变化；同一部署不能悄悄混用两套金额口径。

## 4. 生命周期与历史数据

| 动作 | 必须执行 | 数据处置 |
| --- | --- | --- |
| 安装 | 校验包来源、依赖、接口、迁移扫描与契约测试；隔离副本演练；部署并重启 | 未显式启用的公司不自动开始处理历史业务 |
| 启用 | 权限/参数检查、前置插件检查、管理员确认版本；记录审计 | 历史事件是否补投按插件升级方案明确，不默认全量重放 |
| 停用 | 有启用中的依赖方则拒绝；阻断新命令和任务；保留队列 | 历史只读查询、附件、账本与审计继续可用 |
| 升级 | 备份；先扩展结构再迁移；兼容测试和历史重算比对；检查积压事件 | 已过账金额保持原值；口径变化用开放期间调整事件 |
| 回退 | 回退到与当前结构兼容的代码；恢复原启用版本 | 不倒放财务事件或删除迁移；必要时采用整库与附件恢复 |
| 移除代码 | 所有公司停用、依赖解除、事件归档、保留读取历史所需摘要 | 默认不删表、不删来源、不清空待办；数据清理是独立且可审计的运维操作 |

“可拔插”指可独立启停和升级、边界内替换，不承诺任意 Python 代码在运行中热装。安装、升级与数据库结构变化仍走部署流程。同进程受信插件不具备故障进程隔离；不受信扩展放到独立服务，经窄权限 API 交互。

## 5. 从当前版本迁移

1. 先做 WO-14：公共服务接口、命名空间注册、入口统一 guard、迁移检查和契约测试。既有表及主键不动。
2. 抽离 delivery 的纯策略与页面，再抽离 time 的命令和视图；用旧 API 的适配层维持当前浏览器、CSV 和 MCP 行为。
3. 新合同、结算和其他财务对象直接建在各自插件 App，不继续把业务表追加到 core。现有工时/单据/账本先保留表名和迁移归属，避免一次搬表影响历史来源。
4. costing 与 cash 接管现有业务服务时，先做只读并行比对；切换写入口后，旧入口只转发，不保留两套规则。
5. 最后移除旧实现和适配层，前提是历史数据、现有接口和停用场景均通过验收。全程允许数据库向前扩展，禁止一次性搬库重写。

因此未来工作单必须先经过 WO-14 的文件所有权调整。当前 WO-01 至 WO-09 描述了领域规则，所列 core 文件范围是工程验证版的接线位置；开工前必须改为对应插件目录并冻结契约，不能照旧扩张大 core。

## 6. 每个插件的验收包

- 正常流程、金额守恒、重复请求、过期版本、跨公司、跨项目、角色降级、自审和锁期反例。
- 启用、停用、有依赖时停用、升级失败、队列保留与重启后重放。
- 停用后所有旧 URL、API、CSV、MCP、后台命令均无越权写；历史账本和凭证仍可查询。
- 新旧版本在同一匿名化夹具上逐分比对；数据库真实多连接验证并发；SQLite 结果不能替代 PostgreSQL。
- 内核当前版及约定兼容版本的 CI，独立实现者和复核者的结论，真实执行记录。

低成本模型每次只处理一个扩展点或一个业务薄片；工作单固定输入、文件所有权、schema、反例与退出条件。测试失败先修具体缺口，不能以弱化权限或删除反例换取通过。
