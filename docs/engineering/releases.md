# 分支、版本与发布

日期：2026-10-22。本文规定分支模型、版本号、标签、hotfix 与回滚。0.1.0曾生成本地源码包；公开GitHub发布状态另以远端记录为准。任何版本、标签或 CI 结果以 Git 历史与实际运行记录为准，不从文档推断。

## 1. 分支模型

小团队 trunk-based 开发：

- `main` 是唯一主干，始终保持「CI 通过、可发布」状态；所有工作经短分支与 PR 合入。
- 短分支命名 `feat/PH-001-x`（任务 ID 加简述），修复用 `fix/PH-002-x`，紧急修复用 `hotfix/PH-003-x`。一个分支对应一个任务，寿命以天计，完成后删除。
- 不在 main 上直接提交；不建长期并行开发分支。需要并行的多任务按 agent-protocol.md 的写范围互斥规则各开分支，由集成者串行合入。
- main已启用保护：PR、8项required checks、strict最新BASE、讨论解决、线性历史，管理员同等执行，禁止force-push和删除。单维护者GitHub审批数为0，S级仍须独立Agent审阅报告。合并前核对当次全部检查与未解决review，不能绕过保护。

## 2. 版本号：SemVer < 1.0

当前处于 0.x 阶段，规则如下：

- 版本格式 `0.MINOR.PATCH`。MINOR 增加表示新增能力或口径变化，0.x 阶段允许在 MINOR 中做不兼容变更，但必须在 CHANGELOG 显式标注破坏性与迁移要求；PATCH 只装向后兼容的修复，不改契约、不改口径。
- 破坏性变更集中进 MINOR，不在 PATCH 里夹带；金额、状态机、权限、API、AI 契约的变更永远按 S 级任务走，无论落在哪个版本位。
- 标签格式 `v0.MINOR.PATCH`，打在 main 的发布提交上。标签是发布动作的一部分，不事后补标历史提交冒充当时已发布。
- 1.0 的门槛不由日期决定：至少要求 delivery-status 中生产关键未验证项（PG 并发、备份恢复演练、容器部署）完成验证，具体门槛由用户在接近时拍板。

## 3. 发布流程

1. 确认本次包含的任务全部满足 Definition of Done（lifecycle.md 第 3 节），CI 在待发布提交上实际通过。
2. 更新 CHANGELOG.md：新增能力、修复、破坏性变更、迁移要求、未验证事项的变化。
3. 更新 docs/delivery-status.md：分别说明代码存在、自动化通过、浏览器检查、生产验证；检查范围之外的事项明确保留。
4. 打标签 `vX.Y.Z`；生成源码包并校验（`scripts/package.py` 与 `scripts/verify-source-package.py`）。runtime、.env、虚拟环境、附件与备份不进入发布包。
5. 发布记录写进交接证据（`project/handoffs/` 与 `project/reports/`，位置见 agent-protocol.md）。
6. 发布后发现缺陷：修复走 PATCH 或 hotfix（第 4 节）；已发布版本不撤回标签、不改写已发布内容，修正以新版本呈现。

## 4. hotfix 与补丁

- 触发条件：已发布版本存在影响资金、权限或数据完整性的缺陷，或系统不可用。
- 流程：从对应发布标签拉 `hotfix/PH-xxx` 分支，最小修复，反例测试先行；S 级复核不省略（可用低成本独立代理，见 lifecycle.md 第 4 节）；合回 main 后立即发 PATCH 版本并打标签。
- hotfix 不修两件事：不顺手重构、不夹带新功能。范围膨胀按 recovery.md 处理。

## 5. 回滚

区分代码回滚与数据回滚，两者规则不同：

- 代码回滚：用新版本回退（revert 提交或发布旧版镜像），不使用 force-push 改写 main 历史。回退版本必须与当前数据库结构兼容；不兼容时先按迁移规则处理再回退。
- 迁移与数据：不倒放迁移、不删除迁移文件、不直接编辑账本与审计历史。财务纠错追加负值冲销；确需整库恢复时按 docs/operations.md 的备份恢复路径，在隔离环境演练后执行。
- 已部分发布的任务取消：见 recovery.md 矩阵第13项，先冻结口径再决定冲销或继续，不留半套规则在线。
- 回滚本身是 S 级动作：记录回滚原因、影响的数据范围、冲销方案与验证证据，独立复核后执行。

## 6. 版本事实的来源

「哪个版本包含什么、是否通过验证」以三处交叉为准：Git 标签与历史、CHANGELOG.md、docs/delivery-status.md 及对应交接证据。三者矛盾时以 Git 与 CI 运行记录为准并当次修正文档。聊天记忆里出现过的「已发布 / 已通过」不构成事实。

## 7. 自动发布与可重试分支

版本唯一来源是pyproject.toml；健康接口和源码包读取同一版本。公开标签使用vMAJOR.MINOR.PATCH，release_check验证版本、CHANGELOG与1.0就绪门槛；0.x在GitHub标为pre-release，不表示生产可用。

标签触发release.yml，先对同一提交重跑全部检查，随后创建draft、上传ZIP与SHA256、下载远端资产逐字节核对，最后转公开。重试只能修复同一提交的draft；已经公开且摘要一致时幂等返回，目标或内容不一致则拒绝，不覆盖公开资产。不要为了重试移动标签。

较旧版本的hotfix需要先把任务契约以规划PR加入对应维护分支；不能用当前main契约猜测旧标签上的范围。修复提交向main前向合并或cherry-pick，重新CI；没有维护分支时先为受支持版本明确建分支，不承诺同时维护所有历史0.x。

发布事实先于后续文档回填：被打标签的源码快照不能自行证明随后的发行成功。以同提交发行workflow、GitHub Release的公开状态与下载资产SHA256为准；不能为修改这句状态反复移动标签或覆盖公开资产。
