# 任务生命周期：需求到交接

日期：2026-10-22。本文规定任何变更（功能、修复、文档、工程件）从提出到交付的必经环节与进出标准。术语：「主代理」指当前任务的技术负责人（人或 agent）；「执行者」指实际改代码的代理；「复核者」指与实现者不同上下文的独立代理。

## 1. 流程总览

```text
需求 → 任务 ready → 实现 → 独立审阅 → CI → PR 合并 → 发布 → 交接
```

每个环节有明确的进入条件和产出，跳过环节完成的任务不算完成。小修复可以合并环节（例如实现后由主代理走集成审阅清单），但 S 级任务的独立复核不可合并，见第 4 节。

### 1.1 需求

任何变更先落到一段可核对的描述：解决什么问题、涉及哪些业务口径、不做什么。需求文档（product-requirements.md、accounting-rules.md、work-orders/）描述的是目标设计，其中大部分尚未实现；原 WO-01 至 WO-14 是领域详细规格，开工前必须拆成 PH 编号的小任务并冻结契约，不能直接照 WO 的 core 文件范围开工（依据 plugin-evolution.md 第 5 节）。

### 1.2 任务 ready

任务达到第 2 节 Definition of Ready 才允许排入实现。任务契约以仓库 `project/tasks.json` 版本为准（见 agent-protocol.md 第 3 节）；GitHub Issue 只是讨论镜像，不构成 ready 依据。

### 1.3 实现

执行者按任务契约的文件白名单实现，先写反例测试再实现（development-contract.md 第 2 节）。实现中发现契约本身有问题，停下来走变更，不在实现里悄悄改：契约变更写明旧口径、新口径、影响面、迁移与数据处置，由主代理批准。

### 1.4 独立审阅

- A/B 级：主代理按 development-contract.md 第 6 节集成审阅清单审阅。
- S 级：必须由与实现者不同上下文的独立代理复核，复核者只拿契约、差异和测试，不看实现者推理过程；复核者可用低成本合格模型，GPT 级模型不是硬性依赖。复核结论是「通过 / 打回加具体缺口」，打回最多纠正两次，之后主代理接管（development-contract.md 第 4、5 节）。
- 个人仓库现阶段不强制第二个 GitHub 账号 approve；独立代理复核记录不等同于独立 GitHub 身份。复核记录作为交接证据保存在 `project/reports/<id>.json`（位置冻结见 agent-protocol.md，目录已建立，每次任务交付者提交证据）。

### 1.5 CI

PR 必须通过 required CI 再合并。CI 定义见 `.github/workflows/test.yml`（当前含 PostgreSQL 服务、主测试、迁移检查、verify_integrity、MCP 测试）。配置文件存在不等于某次 CI 已通过；每次合并以当次 PR 的实际运行记录为准。当前不承诺已启用远端分支保护，合并纪律靠流程约束：不经 PR 与 CI 不合并到 main。

### 1.6 PR 合并

PR 描述面向没看过对话的审阅者：问题和行为变化、风险级别、验证证据、未验证事项。一个 PR 对应一个任务；范围膨胀按 recovery.md 处理。默认squash保留一个任务的完整变化，提交标题采用 feat(PH-001): ... / fix(PH-001): ... / chore(PH-001): ...。

### 1.7 发布

达到发布条件时按 releases.md 执行：版本号、CHANGELOG、标签、验证证据、delivery-status 更新。发布是显式动作，合并到 main 不等于发布。

### 1.8 交接

任务结束时产出交接证据：`project/handoffs/<id>.md`（人读：做了什么、为什么、剩什么）与 `project/reports/<id>.json`（机器读：任务标识、文件差异、验收命令与结果、复核结论、未验证事项）。机器事实不依赖聊天记忆，后续代理只看仓库与 CI 即可接手（agent-protocol.md 第 2 节）。

## 2. Definition of Ready

任务进入实现前必须同时满足：

1. 有唯一任务 ID（PH 编号）与一句话目标，能从需求或 WO 追溯到来源。
2. 契约已冻结：字段与类型、状态机、权限矩阵、幂等键、金额与时间口径按 development-contract.md 第 1 节逐项明确；缺少的项写明「本任务不涉及」并说明理由。
3. 文件白名单与禁止范围明确，与其他进行中任务的写范围互斥；共享接线文件（`pmo/urls.py`、导航模板、`core/views.py` 既有函数）不在白名单内，由集成者接线。
4. 至少一个「能使错误实现失败、正确实现通过」的反例测试已写明。
5. 验收命令明确（默认即 AGENTS.md「验收与交付」四条；涉及 MCP 加 integrations/mcp 独立测试与 stdio 握手）。
6. 风险级别（S/A/B）已标注，S 级已指定独立复核安排。
7. 依赖已确认：所依赖的任务已交付，或明确说明本任务可以在其之前完成。
8. 未验证事项的预期边界已写明（例如「本任务只做 SQLite 验证，PG 并发留待 WO-10」）。

任何一项不满足，任务停在 ready 之前，由主代理补齐或退回需求方。不满足 ready 就「先做起来」是范围膨胀与返工的主要来源。

## 3. Definition of Done

任务交付必须同时满足：

1. 验收命令全部实际运行通过，输出留存在 `project/reports/<id>.json`；人工「看着对」不算。
2. 反例测试真实失败过再被实现改绿（或能说明为何不适用）；既有测试未删除、未放宽，确需修改既有用例时在交付 JSON 的 deviations 里说明理由。
3. 权限、金额、幂等、审计、迁移、模板与 API 六项按 development-contract.md 第 6 节清单核对完毕；S 级附独立复核结论。
4. 迁移只追加、不原地修改已应用迁移；含迁移的任务由集成者串行集成，序号按当前迁移叶节点生成。
5. 文档同步：delivery-status.md 更新「实现了什么、证据是什么、还有什么没验证」；行为或口径变化同步对应契约文档。禁止把规划写成已实现。
6. 未验证事项显式列出（例如未在 PG 运行、未做真实模型调用）；不得以配置存在代替运行证据。
7. 交接证据（handoff 与 report）已按 agent-protocol.md 第 3 节的位置入库。
8. 后续任务已识别：本任务留下的差距要么转为新 PH 任务进入 tasks.json，要么写明「不做」及理由。

## 4. 风险分级

| 级别 | 范围 | 复核要求 |
| --- | --- | --- |
| S | 金额与核算口径、权限与租户、迁移与历史数据、对外 API 契约、插件 kernel 与 outbox、锁账/冲销/并发 | 独立代理复核（与实现者不同上下文），测试含越权或并发反例；机器验收全过 |
| A | 常规业务：表单、视图、模板、报表聚合、CSV 列、文档 | 主代理集成审阅 |
| B | 结构清晰的实现：按冻结契约的新对象 CRUD 与状态机、工程脚本 | 主代理集成审阅，关键断言抽查 |

分级在 ready 阶段标注；实现中触及 S 级范围（例如原本只是表单的任务需要加迁移）立即升级并按 S 级补齐复核。金额、状态机、权限、API、AI 契约的契约变更一律按 S 级处理。

S 级复核不依赖特定高价模型：复核者只需拿到契约、差异和测试逐项核对，低成本合格模型即可承担；GPT 级模型仅作为疑难问题的可选升级手段（development-contract.md 第 0 节）。

## 5. 判断与请示边界

- 业务口径（金额怎么算、状态怎么流转、谁能看什么）不明确时，找用户给出具体待判断项，列清楚选项和影响；不替用户拍板，也不把技术验证当业务判断。
- 普通技术选择（目录组织、命名、实现手法、不改契约的重构）由主代理按仓库既定决策自行决定，不反复请示。技术栈与依赖固定，新依赖、新端点必须主代理批准（development-contract.md 第 2 节）。
- 拿不准时先查仓库事实、既有ADR和用户已授权范围；只有无法自行解决且影响业务含义的判断才询问用户，同时继续不依赖答案的工作。

## 6. 变更的通用要求

- ADR：涉及架构取舍（新组件、新扩展点、契约变更）在 `docs/` 增补或修订对应设计文档，写明决定、备选与代价；单文件小决策写在交接 handoff 里即可。
- 测试：先反例后实现；并发与生产口径用 PostgreSQL 验证，SQLite 结果不能宣称生产并发正确。
- 迁移：只追加；append-only 触发器不被绕过；纠错用负值冲销，不改历史行。
- 幂等与兼容：写路径保持幂等键语义；内核 API 兼容期内只做向后兼容增加，破坏性升级走新主版本（plugin-evolution.md 第 3 节）；同一部署不混用两套金额口径。
