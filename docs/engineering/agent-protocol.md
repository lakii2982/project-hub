# 多代理协作与机器事实

日期：2026-10-22。本文规定多个 coding-agent（含人）并行参与本仓库时，事实以什么为准、任务怎么分、写范围怎么互斥、交接证据放哪里。执行渠道遵循AGENTS.md；仓库不依赖特定模型、订阅或个人工具配置。

## 1. 适用范围

任何以代理身份在本仓库执行任务的会话，包括主会话与子代理。人的参与者同样受写范围与交接规则约束。是否派遣代理、派遣几个由主代理决定，本文只规定派遣之后的事实与边界。

## 2. 机器事实：不依赖聊天记忆

仓库的长期事实只来自三类机器来源，任何会话的聊天记录不构成事实：

1. 项目元数据：`project/manifest.json` 与 `project/tasks.json`（版本化任务契约，见第 3 节）。
2. Git：分支、标签、提交历史与文件差异。
3. CI：`.github/workflows/test.yml` 定义的检查在每次提交上的实际运行记录。

推论规则：

- 「做过什么」以 Git 与交接证据为准；「验证过什么」以当次 CI 与 reports 里留存的命令输出为准；「现在能做什么」以 delivery-status.md 为准。
- 配置文件存在不等于 CI 已通过；测试在 SQLite 通过不等于 PostgreSQL 并发正确；任务写进 tasks.json 不等于已实现。
- 新会话开场不询问「上次进行到哪」，而是读 manifest/tasks、Git 状态和最近的 handoff。三处缺失或矛盾时，以 Git 与 CI 为准并当次补齐文档。

## 3. 冻结位置

以下路径是跨代理共享的契约位置，命名与职责冻结，变更按 S 级流程处理。这些位置已经建立；每次接续仍须运行检查，不从目录存在推断任务完成。

| 位置 | 职责 | 维护者 |
| --- | --- | --- |
| `project/manifest.json` | 项目级元数据：当前阶段、活动任务集合、冻结契约清单的指针 | 主代理 |
| `project/tasks.json` | 版本化任务契约：PH 任务的 ID、目标、白名单、风险级、验收命令、状态 | 主代理 |
| `project/handoffs/<id>.md` | 每任务人读交接：做了什么、为什么、剩什么、给下一个执行者的提示 | 任务交付者 |
| `project/reports/<id>.json` | 每任务机器读证据：任务标识、文件差异摘要、验收命令与实际结果、复核结论、未验证事项 | 任务交付者 |
| `scripts/projectctl.py` | 只读任务工具：`check`（契约完整性）、`next`（可开工任务）、`brief <id>`（任务简报）、`verify-change --base REF --task ID`（按BASE白名单和提交报告核对差异，不执行报告里的命令） | 主代理集成；实际运行证据见PH-000报告 |

规则：

- `tasks.json` 是任务范围与验收的唯一权威。GitHub Issue 与 labels 只是讨论镜像：讨论、截图、用户反馈可以留在 Issue，但任务范围、状态与验收以仓库内 tasks.json 的版本为准，不在两处维护互相矛盾的状态；Issue 里的结论要落回 tasks.json 才生效。
- 原 WO-01 至 WO-14（docs/work-orders/）是领域详细规格，描述目标设计。开工前必须由主代理拆成 PH 小任务并写入 tasks.json，文件范围按 plugin-evolution.md 第 5 节落到对应插件目录，不照旧扩张 core。
- handoff 与 report 每任务各一份，先写 report 的验收证据再写 handoff 的叙述；两者矛盾以 report 的机器记录为准。

## 4. 并行与写范围互斥

1. 每个并行任务有互不重叠的文件白名单；白名单之外一律不碰，共享接线文件（`pmo/urls.py`、导航模板、`core/views.py` 既有函数）由集成者在合并阶段接线。
2. 含迁移的任务串行集成；并行执行者不预占迁移序号，由集成者按当前迁移叶节点生成下一号。
3. 集成者（主代理）负责：合并顺序、迁移编号、共享文件接线、delivery-status 汇总更新、最终机器验收。执行者不更新 delivery-status 的汇总口径，只交自己任务的证据。
4. 子代理默认不再派遣子代理；跟进或关闭代理复用工具返回的原始 ID，不手工改写。
5. 取消代理：任务被取消或主代理接管时，先停止该代理的写操作，回收其分支与差异供审阅，再关闭代理；已产生的交接证据（哪怕是失败记录）保留，不删改历史。

## 5. 复核与合并纪律

- S 级任务必须独立代理复核（与实现者不同上下文），复核者可用低成本合格模型，GPT 级模型非硬依赖；复核结论与证据进 `project/reports/<id>.json`。
- 个人仓库现阶段不强制第二个 GitHub 账号 approve；独立代理复核记录不是独立 GitHub 身份，两者不互相冒充。未来增加协作者时，S 级合并要求升级为独立 GitHub 身份 approve，届时修订本文。
- 合并到 main 必须经 PR 且当次 required CI 实际通过；main远端保护已启用且包含管理员；8项required checks、strict最新BASE、讨论解决与线性历史必须满足，不能依靠流程文字代替实际设置。
- 主代理对整合与验收负最终责任：未收到执行结果、未确认工具执行或未通过验收，不得报为完成；高后果改动由主代理亲自复核。

## 6. 真实现状与研发主控

产品能力与已验证范围统一见 [delivery-status.md](../delivery-status.md)，每次核对当前 Git/CI，不继续维护本节旧的 95 项测试快照。GPT 主控、GitHub 需求缺陷与本地执行器的新增目标见 [ai-native-delivery.md](ai-native-delivery.md)。该架构用于研发，独立于产品个人 Agent API；规划不构成已实现能力。

## 7. 治理门禁的信任边界

verify-change只检查已提交的差异。报告中的pass、评审者名称和evidence是声明，CI要重新执行实际测试；它不能证明模型身份、业务判断正确或独立审阅确实发生。

PR的检查器和包装器从BASE读取，任务也从BASE读取，不能通过同时修改HEAD检查脚本或白名单让当前任务自我放行。具有仓库写权限的人仍可能修改workflow或伪造报告；这些变更按S级独立审阅，不能把该机制宣传成对仓库管理员的防篡改沙箱。

每个实现PR正文必须有且只有一行 `Task: PH-001`（换成实际ID），并提交对应报告。首次建库的main初始化是唯一例外；初始化后的收口也用PR演练。Dependabot PR同样需要维护者或Agent补任务、评审与报告，不自动合并依赖升级。

Dependabot提案没有Task行而被治理检查拒绝时，先评估升级必要性、兼容性与许可，用规划PR登记并冻结独立PH任务；契约合入后，再将需要的升级应用到该任务短分支，保留原机器人PR链接，提交验收和报告。被取代的机器人PR可关闭，不把依赖大版本提案直接当作开工授权，也不通过补一行Task或关闭检查来绕过尚未冻结的契约。

## 8. 续接、接管与任务编号

编号PH-001起，允许3至6位数字，避免长期项目在第1000项任务时改格式。编号不复用；取消任务保留，新的实现使用新编号。PH-090是首个规划工作槽，完成后创建下一个规划任务，不让同一done任务反复冒充新迭代。

新会话先处理active_handoff指向的未完成工作，再选next中的ready任务。用户明确要求切换Agent并继续某任务时，可以接管该任务：记录旧执行者、新执行者、分支/提交、接管原因和重新验证结果，不等待旧模型响应。若旧执行者仍在写同一范围，先停止旧写入或用独立worktree隔离；不能因时间过去就假定锁已释放。

无法判断并行写入归属时，保留原工作树和未提交差异，在独立分支/worktree重建已确认部分；不自动stash、reset、清理用户文件。取消任务时同步处理依赖者：改为blocked并说明缺失依赖，或经规划PR替换依赖；取消不算done。
