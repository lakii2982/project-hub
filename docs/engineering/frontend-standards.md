
# 项目中枢前端工程与验收约束 v2.0

- 产品：项目中枢（PROJECT HUB）
- 适用范围：Django 模板、全局与页面 CSS、原生 JavaScript、本地 SVG、共享 partial 及前端验收证据。
- 配套文件：`visual-system.md` 定义视觉语言，`ui-tokens.css` 定义唯一语义令牌，`ui-specimen.html` 提供参考实现。
- 优先级：仓库现行业务契约、财务口径与权限规则 > 本规范 > 外部设计参考包。
- 本规范约束实现与验收，不代表任何产品页面已经完成改造。

## 1. 强制约束

1. 所有颜色、间距、圆角、阴影、层级、字体与尺寸必须使用 `ui-tokens.css` 中的语义令牌；禁止新增页面私有十六进制色值、私有色名、私有间距体系或硬编码阴影。
2. 已有共享组件能够满足需求时必须复用，不得在各页复制页头、页签、表格、表单、徽章或空态后仅修改颜色与文字。
3. 实现仅使用 Django 模板、原生 HTML/CSS/JavaScript 与本地 SVG；禁止引入构建链、CDN、远程字体、远程脚本、第三方组件库或新依赖。
4. 正文不得小于 14px；表格与辅助文字不得小于 12px；不得通过缩小文字解决空间不足。
5. 金额、工时、比例等需要对齐的数值使用 `font-variant-numeric: tabular-nums`；金额右对齐，不得使用等宽字体替代等宽数字。
6. 页面采用左侧选择模块、右侧模块内页签的结构；每个页签只显示当前面板，不得恢复为模块内长滚动页面。
7. 产品界面只保留标签、数值、状态徽章、缺口计数、操作和空态下一步；禁止解释性长段落、公式小字、卡片副标题及重复口径说明。
8. 业务口径差异只使用极短短语，例如「合同额≠收入」「毛利≠现金净额」，不得在大段说明中重新定义业务。
9. 前端不得新增业务审批阶段、权限规则、金额口径、成本口径、状态迁移或数据计算规则。
10. 金额以服务端整数分及其格式化结果为准，工时底层以整数分钟为准；展示单位为小时时也必须使用服务端提供的展示值。
11. 费用确认成本、付款确认现金，同一支出不得重复计入；计划不得展示为实际，过期计划不得由前端自动挪周。
12. 净现金流、利润与银行余额不得互相替代；缺少数据时不得显示假零，必须使用缺口徽章或缺口计数。
13. 禁用按钮只表示当前操作不可执行，不得作为权限控制；无权限必须由业务层判定，并使用明确的不可用状态。
14. 所有页面必须满足键盘操作、清晰焦点、状态非纯色表达、200% 文字缩放和 `prefers-reduced-motion` 要求。
15. 视觉改造不得停留在换色；布局、页签、状态、响应式和交互必须同时达到本规范。

## 2. 文件与组件组织

### 2.1 现有结构与职责

- `templates/base.html`：应用壳层、侧栏容器、页头容器、跳到主内容链接、全局反馈区域及主内容 landmark。
- `templates/partials/`：跨模块共享的结构化组件，不承载单个页面的业务计算。
- 各插件模板：只组合共享 partial，提供业务数据、当前页签和面板内容。
- `static/app.css`：全局样式入口，引用唯一语义令牌并承载共享组件样式。
- `static/app.js`：全局渐进增强，包括页签、移动导航、对话框和必要的通用交互。
- `static/icons.svg`：本地 SVG 图标精灵；图标引用必须提供可访问名称或按纯装饰隐藏。
- `static/ui/ui-tokens.css`：生产环境加载的语义令牌文件。
- `docs/engineering/ui-tokens.css`：规范侧的同一令牌源文件，与生产文件内容保持同步。

### 2.2 共享 partial

共享组件使用以下固定名称：

- `templates/partials/app_sidebar.html`：模块导航、当前模块、移动菜单入口。
- `templates/partials/page_header.html`：页面标题、必要操作和极短口径提示，不放解释性副标题。
- `templates/partials/tabs.html`：页签列表、选中态、深链和面板关联。
- `templates/partials/filter_bar.html`：筛选控件、已选条件、清除与提交操作。
- `templates/partials/data_table.html`：表格标题、列头、数值对齐、空态和窄屏字段行卡。
- `templates/partials/form_field.html`：永久标签、必填标识、帮助信息、控件与错误关联。
- `templates/partials/status_badge.html`：本地图标或形状、中文状态文字及语义类型。
- `templates/partials/empty_state.html`：空态原因、缺口信息和唯一下一步操作。
- `templates/partials/feedback.html`：成功、警告、错误、不可用反馈及错误摘要入口。

页面模板只做布局组合，例如壳层、页头、页签、当前面板及面板内组件；不得在页面模板中另造一套共享组件结构。

### 2.3 新组件与命名

- 新组件优先放入共享 partial 和 `app.css`；仅在确无复用价值且不影响其他页面时才允许页面级样式。
- CSS 类名沿用 `app.css` 的全局命名空间和 BEM-ish 结构，采用 `组件__元素--修饰` 形式，例如 `data-table__amount`、`status-badge--warning`。
- 不使用意义不明的缩写、按页面颜色命名的类名或通用全局类名，例如 `.blue`、`.box`、`.mt10`。
- 新增共享模式时，同次变更必须更新 `visual-system.md`、本规范、`ui-tokens.css` 与 `ui-specimen.html`；四者不得分批漂移。
- 样张负责证明共享模式，产品页面负责证明真实业务集成，两者不能互相替代。

## 3. 令牌使用与断点

### 3.1 角色映射

- `canvas`：主画布，固定对应 `#F7F9FD` 的语义角色；不得作为卡片背景。
- `surface`：卡片、侧栏和主要内容表面；不得用于表达成功或选中。
- `text`：主文字、次要文字、辅助文字及禁用文字的分层角色；不得直接写裸色值。
- `accent`：品牌蓝、当前模块、当前页签和主要交互；普通装饰、统计图形或多个并列按钮不得滥用。
- `success`：已完成、已确认等正向业务状态；不得替代 `accent` 表示当前选中。
- `warning`：临期、待处理、计划缺口等提醒；不得用作普通装饰。
- `danger`：失败、逾期、危险操作等风险状态；不得仅因数字为负就自动套用，须遵循业务状态。
- `info`：中性提示与信息状态；不得与 `warning` 互换。
- `focus`：2px 焦点环；必须清晰可见且不被 `overflow` 裁切。
- `chart`：图表序列令牌；按数据系列使用，不得把图表颜色另作业务状态判断的唯一依据。
- 间距统一使用 `--space-*`，遵守 4px 网格；主区桌面留白 32px，窄屏 16px，区块间距 16px，卡片内距 16–18px。
- 卡片圆角 14px、按钮 9px、输入框 8px、标签 999px；均引用对应圆角令牌。
- 阴影仅用于菜单、对话框等浮层，卡片不得依靠重阴影分层；浮层必须使用层级令牌。

### 3.2 禁止裸值与语义混用

- 产品 CSS 中不得出现新的 `#2563EB`、`#1D4ED8`、`#EAF1FF` 等裸色值，即使与令牌数值相同。
- 禁止 `style="color:#0F1D33"`、`style="margin:13px"` 等页面私有内联样式。
- 不得为了「更接近设计稿」新增同义令牌；先确认现有角色，确需新增时同步四文件。
- 状态色不得用作纯装饰，主色不得用于表达成功，危险色不得用于普通数字强调。
- 第三方参考包中的品牌名、色名、示例金额和权限示例不得直接成为产品事实。

### 3.3 加载、同步与检索

- `static/app.css` 必须通过 `@import url("ui/ui-tokens.css");` 加载生产令牌，且该引用位于其他样式规则之前。
- `static/ui/ui-tokens.css` 与 `docs/engineering/ui-tokens.css` 必须同源同步，不得形成两套不同语义令牌。
- 同步后使用 `diff -u docs/engineering/ui-tokens.css static/ui/ui-tokens.css` 验证内容一致。
- 修改令牌名称或语义前，必须检索全部模板、CSS、JavaScript、SVG 和样张使用点，并在同次变更中更新。
- 禁止通过旧值覆盖、新值补丁或页面级变量继续保留废弃令牌。

### 3.4 断点

- 必检与布局参考断点为 390、640、768、1024、1440px。
- 1024px 及以上使用 240px 白色侧栏；低于 1024px 使用模态导航抽屉。
- CSS 自定义属性不能用于媒体查询条件，因此媒体查询必须使用字面值。
- 每个媒体查询字面值必须与 `ui-tokens.css` 中对应断点注释同步；修改任一处必须同次修改另一处。
- 不得只验证几个离散截图而忽略中间宽度；必须检查 320px 至宽屏的连续宽度变化。

## 4. 布局与页签实现

### 4.1 应用壳层

- 桌面结构为 240px 白色侧栏加主区；主区包含页头、页签和唯一当前面板。
- `main` 具有稳定 ID，供跳到主内容链接使用；页面标题使用唯一 `h1`。
- 页头只包含标题、当前上下文和必要操作，不堆叠口径说明或多个重复面包屑。
- 主区桌面留白 32px，卡片内距 16–18px，相邻区块间距 16px。
- 表格桌面行高约 44px，金额右对齐并使用等宽数字；展开行不得改变整表宽度。

### 4.2 模块页签与默认页签

- 工作台：收益与现金（默认）、到期提醒、项目动态。
- 项目：项目列表，作为唯一默认面板，不制造无内容的额外页签。
- 项目详情：概览（默认）、关键任务、里程碑、项目财务、风险、团队。
- 工时：按周填报（默认）、工时明细、项目汇总。
- 费用：登记费用（默认）、待确认、8 周计划、全部记录。
- 现金流：概览（默认）、发票、收款、资金账户、8 周计划。
- 设置：成员（默认）、成本费率、审计日志。
- 页签清单、顺序、默认项和文案必须与 `visual-system.md` 一致；变更必须同步更新两份规范与样张。

### 4.3 页签语义与键盘行为

- 容器使用 `role="tablist"` 并提供 `aria-label`；页签使用 `role="tab"`，面板使用 `role="tabpanel"`。
- 当前页签设置 `aria-selected="true"` 和 `tabindex="0"`，其余页签设置 `aria-selected="false"` 和 `tabindex="-1"`。
- 每个页签通过 `aria-controls` 指向稳定面板 ID；每个面板通过 `aria-labelledby` 指向对应页签 ID。
- 同时只显示一个面板；若多个面板存在于 DOM，非当前面板必须使用 `hidden`，不得仅靠透明度或移出屏幕隐藏。
- 采用手动激活：←/→ 循环移动页签焦点，Home/End 移到首个/末个页签，Enter/Space 激活。
- 激活后更新深链和面板，并将焦点移到新面板标题；标题可设 `tabindex="-1"` 以接收程序化焦点。
- 不用 CSS `order` 改变页签或面板的阅读顺序。

### 4.4 深链与无 JavaScript

- 使用 `?tab=概览对应的稳定面板ID` 形式的查询参数保存当前面板，实际参数值使用稳定英文 ID，例如 `?tab=overview`。
- 页签基本元素使用真实链接；无 JavaScript 时可通过服务器重渲染读取目标面板。
- 无效或无权访问的面板 ID 由服务端处理，不得由前端伪造空数据或越权内容。
- 浏览器前进、后退必须恢复正确页签、面板和焦点，不得出现选中页签与面板不一致。

### 4.5 移动导航抽屉

- 窄屏导航使用原生 `dialog`，不得用普通 `div` 模拟模态框。
- 打开后焦点进入抽屉，Tab 与 Shift+Tab 不得逃逸到背景内容。
- Esc、明确关闭按钮和选择模块后的导航行为必须可预测。
- 关闭后焦点回到菜单按钮；菜单按钮具有可访问名称和展开状态。
- 抽屉关闭动画不得阻碍焦点恢复，并尊重 `prefers-reduced-motion`。

## 5. 数据、状态与完整性

### 5.1 七态要求

每个异步或渐进增强区域必须设计并实现以下七态：

1. 默认：展示已确定内容、必要标签与操作，不预先放置假数据。
2. 加载：保留区域尺寸与布局，使用稳定骨架或加载状态，不造成内容跳动。
3. 成功：展示服务端真实结果，并更新必要的时间和计数文本。
4. 空：没有数据且未应用筛选，提供符合权限的下一步操作。
5. 筛选空：明确当前筛选无结果，保留筛选条件并提供清除操作。
6. 错误：保留用户输入和筛选，说明失败状态并提供重试；不得清空已填内容。
7. 不可用：无权限、功能未开放或依赖不可用时明确表达，不得混用无数据文案。

### 5.2 数据与提交约束

- 无权限与无数据必须使用不同文案、不同后续操作，不得都显示「暂无数据」。
- 状态徽章必须包含图标或形状与中文文字，例如警示图形加「待确认」，不得只显示彩色圆点。
- 缺数据使用缺口徽章或缺口计数；0 只能表示服务端确认的真实零值。
- HTML 与 JavaScript 不重新计算金额、工时、利润、成本、现金或汇总；只展示服务端值。
- 前端格式化不得改变精度、单位、正负号或业务口径。
- 提交中必须防止重复触发，并保留清晰进行中状态；服务端幂等、权限和状态校验仍由业务层负责。
- 请求失败不得仅在控制台记录错误；用户必须看到可重试的反馈。
- 异步更新不得悄悄替换用户正在阅读或编辑的其他区域。

## 6. 表单、审批、敏感操作与登录

### 6.1 表单

- 每个控件都有永久可见标签，标签位于控件上方；placeholder 只能给输入示例，不能替代标签。
- 必填项同时显示「必填」文字和星号，星号不能成为唯一必填提示。
- 帮助文字和错误文字通过 `aria-describedby` 与控件关联，错误不得只用红色边框表达。
- 表单顶部提供错误摘要；摘要有可访问名称，并链接到对应字段。
- 提交失败后聚焦首个无效字段；服务端返回错误与客户端校验错误采用同一呈现规则。
- 筛选、输入和已展开状态在失败重试时按业务允许范围保留，不得无故重置。
- 触控目标至少 44×44px；视觉尺寸较小时通过真实点击区域满足要求，不得重叠相邻目标。

### 6.2 审批与敏感操作

- 审批页固定按「申请事实 → 证据 → 审批记录 → 意见与操作」排列。
- 申请事实与证据只展示业务层提供内容，前端不得推断审批阶段或补充权限结论。
- 审批操作使用明确动词，意见要求与校验遵循现行业务规则。
- 危险或不可逆操作必须说明具体对象和后果，使用明确动词并要求确认。
- 确认框默认焦点不得诱导误确认；取消、Esc 和关闭后焦点恢复必须可用。
- 不用禁用按钮替代权限判断，不向无权用户展示可绕过服务端校验的操作入口。

### 6.3 登录

- 登录页采用单列布局，字段顺序与视觉顺序一致。
- 用户名和密码均有完整永久标签，错误通过摘要与字段关联共同表达。
- 密码可见开关具有可访问名称和状态，切换不得清空密码或改变焦点位置。
- 不自动填充演示凭据，不在页面写入真实客户、工资、账号或凭据。
- 登录失败不得泄露账号是否存在等敏感信息，具体文案遵循业务层约定。

## 7. 响应式规则

1. 1440×900、390×844 和 320px 宽为每次 UI 交付的必检视口，同时检查 320px 至宽屏连续宽度。
2. 任何视口下 `body` 不得产生横向滚动；不得以隐藏整页溢出来掩盖布局错误。
3. 桌面使用侧栏加主区，窄屏使用模态导航抽屉；窄屏主内容留白 16px。
4. 表格默认采用桌面呈现，窄屏转换为带 `data-label` 的字段行卡，字段标签与值保持明确关联。
5. 字段行卡必须保留状态、金额、工时、缺口、操作和展开内容，不得为适配窄屏删除关键数据。
6. 只有确实不可重排的矩阵允许表格容器局部横向滚动，并必须提供可访问名称和明确滚动区域。
7. 筛选和表单在窄屏改为单列；操作按钮可换行，不得挤压到无法阅读或触控。
8. 长中文名称、长编号、大金额和连续字符必须可换行或截断并提供完整可访问内容，不得撑破容器。
9. DOM 顺序必须与视觉及阅读顺序一致，禁止使用 CSS `order` 重排内容。
10. 图表在窄屏调整尺寸和标签密度，但必须保留摘要、单位、图例及等价数据表。
11. 文字放大 200% 时不得遮挡操作、丢失内容或要求双向滚动。
12. 动画和布局变化不得造成明显 CLS；异步内容、图片、SVG 和图标预留稳定尺寸。

## 8. 键盘、焦点与语义

- 页面首个可聚焦元素为「跳到主内容」链接，激活后落到主内容标题或主内容容器。
- 正确使用 `header`、`nav`、`main`、`aside`、`footer` 等 landmarks，并为重复导航提供区分名称。
- 标题层级连续且表达结构，不因字号需要跳级；页签面板标题纳入合理层级。
- 所有功能均可通过 Tab、Shift+Tab、Enter、Space 完成，页签额外支持 ←/→/Home/End。
- 焦点顺序符合视觉顺序，不使用正数 `tabindex` 修补错误 DOM 顺序。
- 页面或页签切换后焦点落到新视图标题；普通表单校验失败则聚焦首个无效字段。
- 对话框必须圈定焦点，关闭后恢复到触发元素；触发元素消失时回到合理的邻近标题或操作。
- 焦点环为 2px，和相邻颜色对比至少 3:1，不被卡片、表格或抽屉裁切。
- 正文文字对比度至少 4.5:1，控件边界、图形关键部分和焦点至少 3:1。
- 图标按钮必须具有可访问名称；纯装饰 SVG 使用 `aria-hidden="true"`，不得重复朗读。
- 表格具有 `caption` 或等价可访问名称；列头使用正确表头语义和范围。
- 数据 SVG 必须提供 `title`/`desc` 或等价数据表；复杂图表同时提供摘要与单位。
- 状态、必填、错误、当前项和图表差异均不得只依赖颜色。
- 尊重 `prefers-reduced-motion`，减少非必要位移、缩放和连续动画，不得借动画延迟交互。

## 9. 前端实现约束

1. Django 模板保持自动转义；禁止拼接未转义的用户姓名、项目名、备注、意见或审计内容。
2. 不对用户内容使用 `safe`，不在 JavaScript 中通过 `innerHTML` 注入未转义业务数据。
3. 动态文本优先使用 `textContent`，URL 和属性值必须来自受控数据并按上下文转义。
4. 不引入新前端依赖，不通过内联远程地址规避无 CDN、无远程脚本要求。
5. JavaScript 仅做渐进增强；核心导航、页签读取、表单和错误反馈不得依赖脚本才能使用。
6. 脚本初始化失败不得阻断整页；正常操作不得产生控制台错误或未捕获异常。
7. 不将凭据、权限明细、敏感经营数据、工资或客户秘密写入 localStorage。
8. 事件监听、DOM 查询和增强逻辑必须可重复初始化，不得造成重复提交或重复绑定。
9. CSS 遵循既有全局命名空间，避免宽泛元素选择器污染其他模块。
10. 图标使用本地 `icons.svg`，不得新增远程图标字体或第三方 SVG 请求。
11. 字体使用系统中文栈，不下载远程字体；数值对齐使用 `tabular-nums`。
12. 页面加载、筛选、页签、展开和反馈更新应避免布局抖动，加载区域保持尺寸稳定。
13. 不在前端硬编码审批流、角色权限或财务计算结果；业务错误必须按服务端响应呈现。
14. 演示内容只能作为演练数据，不得写成真实客户、工资、凭据或经营事实。

## 10. 变更与审查门禁

- 新增交互或视觉模式必须先在同次变更中更新视觉系统、本规范、令牌和样张，再进入产品页面。
- 禁止页面私有令牌、重复页头、重复页签及复制后仅换色的组件实现。
- 令牌变化必须检索并更新全部使用点，同时验证规范侧与生产侧令牌文件一致。
- 本规范 v2.0 冻结后，A 蓝白极简方向不得继续漂移；业务必要变化通过正式规范变更处理。
- 与 `light-delivery.md` 衔接时，队列条目是工作票据，PR 是实现与验收单元。
- 每个 PR 必须列出仓库规定的 9 项必需检查并全部通过，不得以本规范的 UI 清单替代或删减。
- 每个 PR 必须有一次明确作用于当前 HEAD 的独立复核；旧提交复核不得冒充当前 HEAD 复核。
- 每个 PR 必须提供真实浏览器或真实命令演示，输入、操作、结果和适用范围均可核查。
- UI 变更必须提供 Before/After 视觉证据，使用同场景、同视口、同主题和可比数据状态。
- 「配置文件存在」「样张通过」「规范已更新」不得冒充产品页面通过。
- 未运行的检查必须标记 `not_run` 并说明原因；不得写「预计通过」「应无问题」或留空。
- 自动化命令结果与人工浏览器结果分开记录，命令退出码不得由文字描述代替。

## 12. 禁止事项与反例

1. 禁止裸十六进制色值：反例为页面 CSS 写入 `color: #526175`，正确做法是使用次要文字语义令牌。
2. 禁止页面私有间距：反例为 `padding: 19px`，正确做法是使用 `--space-*` 并遵守 4px 网格。
3. 禁止仅用颜色表达状态：反例为绿色圆点表示已确认，正确做法是图标或形状加「已确认」。
4. 禁止 `body` 横向滚动：反例为固定宽度表格撑破 320px 页面后再隐藏整页溢出。
5. 禁止 11px 辅助文字：表格与辅助文字最小 12px，正文最小 14px。
6. 禁止用 CSS `order` 改变阅读顺序：反例为视觉把金额移到标签前而 DOM 顺序不变。
7. 禁止用 placeholder 当标签：反例为输入框只显示「请输入项目名称」且获得焦点后提示消失。
8. 禁止用禁用按钮当权限控制：反例为无权用户看到禁用「审批」按钮而服务端没有权限校验。
9. 禁止页面内注释式长段落：反例为卡片下重复解释利润、现金与合同额的完整公式。
10. 禁止两套并行语义令牌：反例为 `docs` 与 `static` 各自维护不同品牌色和状态色。
11. 禁止只换色不改布局交互：反例为旧长滚动页面改蓝白配色后仍无模块页签和单面板结构。
12. 禁止把静态样张当产品验收：样张通过不能证明真实路由、权限、数据和交互通过。
13. 禁止把演示数据写成真实经营事实：演练金额、客户和人员不得成为产品事实或业务结论。
14. 禁止缺数据假零：反例为成本费率缺失时显示 `0.00`，正确做法是缺口徽章或缺口计数。
15. 禁止前端重算财务口径：反例为 JavaScript 将费用和付款同时相减得到现金净额。
16. 禁止用阴影和颜色掩盖结构问题：反例为所有卡片增加重阴影，却不处理层级、对齐和间距。
17. 禁止正数 `tabindex` 修补顺序：必须修正 DOM，使键盘顺序与视觉顺序天然一致。
18. 禁止远程资源和新依赖：反例为引入远程字体、图标 CDN 或仅用于页签的第三方脚本。
19. 禁止动画引发布局抖动：反例为加载完成后表格、图表和按钮突然下移。
20. 禁止空泛验收声明：反例为「响应式良好」「无障碍已支持」而没有视口、键盘和证据记录。

## 13. 与 v1 的差异与迁移顺序

### 13.1 基线差异

- v1 的 PH-023 冻结基线升级为 v2.0 的 A 蓝白极简 SaaS：白色 240px 侧栏、`#F7F9FD` 画布和语义品牌蓝。
- 页面从模块长滚动改为左侧选择模块、右侧模块内页签，每页签只显示当前面板。
- 工时界面按小时展示，但底层仍遵循整数分钟契约，展示值由服务端提供。
- 产品页面去注释化，仅保留必要标签、数值、状态、缺口、操作和空态下一步。
- 辅助与表格文字下限统一为 12px，正文下限为 14px，不再使用 11px 辅助文字。
- 状态统一为图标或形状加中文的徽章体系，缺失数据统一为缺口徽章或计数。
- 验收明确覆盖 1440×900、390×844、320px 及连续宽度、键盘、七态、200% 缩放和减少动态效果。
- 布局、组件、语义和工程证据同时升级，不接受仅替换色板的视觉漂移。

### 13.2 迁移顺序

1. 壳层：先迁移侧栏、页头、跳到主内容、页签语义、移动抽屉和全局焦点规则。
2. 工作台：依次完成收益与现金、到期提醒、项目动态及各自七态。
3. 项目与项目详情：完成项目列表，再完成概览、关键任务、里程碑、项目财务、风险、团队。
4. 工时、费用、现金流：按既定页签顺序迁移，保持服务端财务与工时口径不变。
5. 设置与跨页图表：完成成员、成本费率、审计日志，并统一图表、图例和等价数据表。
6. 每一步必须独立可验收、可回退，并附真实产品页面证据，不与其他阶段混成不可审查的大变更。
7. 每步完成后同步检查共享 partial、四文件一致性、令牌使用点和旧样式清理范围。
8. 本文件只规定迁移基线与顺序，不在规范内宣称任何阶段或产品页面已经完成改造。
