# Kimi 视觉系统

状态：PH-023 冻结基线。适用于 Project Hub 全部产品前端；本文件定义视觉语言，`frontend-standards.md` 定义工程与验收约束，`ui-tokens.css` 与 `ui-specimen.html` 是唯一令牌和参考实现入口。

## 1. 设计方向

Project Hub 是中文经营 SaaS。界面首先帮助用户看清业务事实、异常和下一步操作，而不是展示装饰。

- **清晰浅色工作台**：中性背景、白色内容面、细分隔线；强调色只用于当前位置、主操作和可交互信息。
- **层级来自排版与留白**：页头、页签、筛选、数据区依次展开，不靠大段英文眉题、渐变、插画或卡片堆叠制造层次。
- **表格优先**：经营数据以可扫描、可比较的表格为主；摘要是表格的辅助，不用数字墙替代表格。
- **稳定而克制**：同层页面使用同一侧栏、页头、页签、间距和反馈位置；圆角、阴影和颜色均少而有意义。
- **信息始终可理解**：状态同时提供文字/图标，图表有形状或线型编码；中文长标题正常折行，金额使用等宽数字。
- **渐进披露**：默认显示常用字段与操作，次要筛选和行详情按需展开，不能用隐藏关键错误来换取“简洁”。

设计借鉴 Linear 的信息层级、导航/页头/页签一致性，以及 Atlassian 的语义令牌、密度和可访问性方法。仅借鉴方法，不复制品牌资产，也不表示使用其官方组件或获得认证。参考链接见 PH-023 契约。

## 2. 布局基线

### 2.1 应用骨架

桌面由固定宽度侧栏与弹性主区组成。侧栏 232px，主区最大内容宽度 1440px；页面内容水平留白 32px，区块间距 24px。侧栏包含产品名、主导航、次要导航和当前用户，不混入页面操作。

页头第一行是可选面包屑，第二行为标题/必要说明与操作区。标题下直接放业务页签；页签之下才是筛选和内容。不得为同一信息重复设置多级标题。

390px 及窄屏使用单列：侧栏改为原生 `dialog` 导航抽屉，页头保留菜单、标题和一个主操作；其他操作进入“更多”菜单或纵向操作区。内容留白 16px，区块间距 16px。禁止通过缩小文字或页面整体横向滚动适配。

### 2.2 密度与对齐

采用 4px 基础网格，常用间距 8/12/16/24/32px。桌面控件高 36px，窄屏触控目标至少 44px；正文 14px，表格和辅助文字不得小于 12px。表单标签、输入和帮助文字左对齐，数字右对齐，操作列固定在语义末尾。

卡片只用于边界明确的独立内容。同页多个摘要指标优先放入一个分段摘要条；数据区、表单区不要层层嵌套卡片。阴影仅用于抽屉、菜单、对话框和即时反馈，普通内容面用边框。

## 3. 导航、页头与页签

- 侧栏每项同时有图标与文字；当前项用浅强调底、文字和 `aria-current="page"`，不能只改颜色。
- 移动导航打开后焦点进入抽屉，关闭后回到菜单按钮；支持 Escape，并阻止背景交互。
- 页面只有一个主操作，使用实心按钮；次操作为描边或文字按钮。危险操作不与主操作并列成相同样式。
- 项目详情页签固定为“概览、关键任务、里程碑、项目财务（有权）、风险、团队”；普通成员仍可从主导航进入“我的费用”查看本人费用。基础资料只包含“项目、员工、成本费率”，不得设计或暗示当前存在客户、供应商对象。页签表达同级视图，不代替步骤条或按钮。
- 页签使用 `tablist`/`tab`/`tabpanel` 语义与选中状态，支持左右方向键及 Home/End；默认只显示当前面板。每个页签是指向面板 ID 的深链，刷新后恢复当前面板；无 JavaScript 时全部面板仍可通过锚点阅读。
- 窄屏页签条在自身容器内局部横向滚动，页签不换行、不截字，页面不得横向溢出；选中页签应滚入可见区域，焦点环不得被滚动容器裁切。

## 4. 数据与经营表达

### 4.1 筛选

主筛选直接显示时间、项目或状态等高频条件，次要条件放入可展开区域。筛选标签始终可见，不能用 placeholder 代替。提供明确“查询”和“清除”操作；已生效条件用可移除条件文本呈现。空结果保留筛选上下文，并提供清除条件入口。

### 4.2 表格与可展开行

表头简洁，数据列按“对象—业务属性—状态—金额/日期—操作”组织。金额、数量和工时右对齐，使用 `font-variant-numeric: tabular-nums`；文本左对齐。每行有充分垂直留白，不以斑马纹代替分隔线。

可展开行使用带 `aria-expanded` 和 `aria-controls` 的独立按钮，按钮可键盘操作；展开内容包含明细定义列表或关联记录，不嵌套另一套完整页面。窄屏表格转为带字段名的行卡片，保持相同信息顺序；若特殊矩阵确需局部横滚，必须只在表格容器内滚动并有可见提示，页面本身不得横滚。

### 4.3 摘要与状态

摘要必须写清业务口径和时间范围；净现金流不得写成利润，预计值不得写成实际值。状态采用“图标/形状 + 中文”：成功用勾，警告用三角，错误用叉，进行中用圆点，草稿用空心形状。语义色不能只靠色觉区分。

### 4.4 趋势图

默认使用原生 SVG 折线/柱形，标题旁标明单位、区间与口径。坐标、来源和图例均有文字；多条线除颜色外再用实线/虚线及不同点形区分。SVG 提供 `title` 与 `desc`，相邻数据表提供精确值；不得用面积渐变、3D 或无意义动画。空数据、加载失败与无权限均显示对应说明，不画误导性的零值线。

## 5. 表单、审批与反馈

表单按业务逻辑分组，标签在控件上方；必填用文字和星号，帮助文字紧邻字段，错误用 `aria-describedby` 关联并在提交后聚焦首个错误。不用 placeholder 充当标签。长表单操作区可吸底，但不得遮挡字段和错误。

审批页先呈现申请事实、金额/期间、提交人和证据，再显示审批记录，最后是意见与操作。通过、退回、驳回必须有不同文字；危险或不可逆操作需要确认，不能仅用颜色表达后果。模型建议只作候选与解释，不获得审批外观或操作特权。

- **空态**：说明没有数据的原因与下一步，区分初始空、筛选空和无权限。
- **加载**：保持布局稳定，使用骨架或“正在加载”状态；不得用空白冒充无数据。
- **错误**：字段错误就地显示；页面错误说明发生了什么、是否可重试，保留用户已填内容。
- **反馈**：即时结果用 `role="status"` 的轻提示；需要处理的错误用 `role="alert"`，重要失败不可只自动消失。
- **不可用**：说明原因与恢复路径，不仅显示灰色按钮；权限不可用时不得暗示操作已执行。
- **登录**：单列、品牌名和简短产品说明，完整标签、密码可见性开关、错误摘要和提交状态；不加入经营数据或装饰插画。

## 6. 响应式与可访问性

以 1440px 桌面和 390px 窄屏为必检视口，同时检查中间宽度。断点只决定布局，不改变业务含义。所有功能支持键盘，焦点环清晰且不被 `overflow` 裁切；DOM 顺序与视觉顺序一致。触控目标至少 44×44px，文本支持 200% 缩放。

正文与背景对比度至少 4.5:1，大字至少 3:1，控件边界和焦点指示至少 3:1。尊重 `prefers-reduced-motion`；动画不是理解状态的前提。图标按钮有可访问名称，装饰图标对辅助技术隐藏。

## 7. 模式扩展与冻结规则

后续前端必须先读本文件与 `frontend-standards.md`，使用 `ui-tokens.css` 令牌和样张共享模式。禁止页面私有色值、临时字体和重复页头/页签实现。现有模式能表达时不得新增模式；确需新增时，先在同次变更中更新本文件、前端规范和样张，再用于产品。

“冻结”指结构、语义与交互基线稳定，不是禁止修正可访问性或缺陷。整合者负责技术验收，不新增业务审批阶段。样张是静态设计参考，不代表产品业务、浏览器兼容、自动化或生产环境已验证。
