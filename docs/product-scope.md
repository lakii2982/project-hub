# 产品范围：小微企业简化版（项目收益与现金流）

状态：2026-11-03 起生效。本文件是 1.0 产品范围的唯一定义；执行顺序见
[../project/QUEUE.md](../project/QUEUE.md)，现状见 [../project/STATUS.md](../project/STATUS.md)，
已定决定与待确认项见 [../project/DECISIONS.md](../project/DECISIONS.md)。

## 1. 为什么重定义

原 1.0 按"专业项目财务系统"设计：合同版本与审批、客户验收/服务期收入确认、应收应付与核销、
预算版本/ETC/EAC、四类核对、月度锁账关期、多币种、工资社保个税。它面向有专职财务的团队，
对小微企业认知负担过高。

2026-11-03 产品负责人判断：面向小微企业的版本太重，用户搞不清复杂财务知识，只想算明白
**项目收益和现金流**，要求简化功能并重新定义产品范围。据此作以下决定（DECISIONS D-09）：

- 1.0 = **小微企业简化版**：以项目为中心，回答"项目赚了多少、钱收回来没有、现金够不够"。
- 专业财务能力移出当前 1.0，代码与数据保留、默认隐藏/停用，后续按需启用（不是删除）。
- 简化的只是产品界面与流程，**不是资金正确性**：金额整数分、Decimal/`ROUND_HALF_UP`、权限与
  租户隔离、审计只追加、来源唯一消费、期间/锁期拒绝路径等底线不变（见 AGENTS.md）。

## 2. 目标用户与要回答的问题

- 目标用户：5–50 人（上限 100 人以下）的软件开发、实施与技术服务公司；老板兼经营决策、可能兼财务；
  没有专职财务、没有 ERP/OA；用浏览器使用自托管实例。
- 老板每周只关心三个问题：
  1. **这个项目赚了多少？** 项目收益（收入 − 成本）
  2. **钱收回来没有？** 已开票、已收款、未收款
  3. **现金够不够？** 现金余额、未来 8 周预计收款与付款缺口
- 一句话定义：用项目串起合同、工时与费用、开票与收款，让老板每周 5 分钟看清项目赚没赚、
  钱回没回、现金够不够。

## 3. 核心链路（1.0 必须端到端可用）

```text
客户 → 项目 → 合同额/收款计划 → 工时与费用 → 开票 → 收款 → 项目收益 + 现金流
```

| # | 用户动作 | 系统结果 | 入口 |
| --- | --- | --- | --- |
| 1 | 建客户、项目、合同额与收款计划 | 项目有合同额、客户、起止与收款节点 | 客户与合同 / 项目 |
| 2 | 成员按周填工时；老板/PM 登记费用或外包支出 | 项目人工成本与直接费用自动汇总 | 工时 / 费用 |
| 3 | 登记一张发票（号码、金额、日期、项目） | 已开票、待开票、未收款发生变化 | 开票与收款 |
| 4 | 登记一笔收款（账户、金额、日期、客户/项目） | 项目现金净额与账户余额发生变化 | 开票与收款 / 现金 |
| 5 | 打开工作台与项目页 | 一屏看到项目收益、未收款、现金与缺口 | 工作台 / 项目 |

## 4. 简化后的计算口径（本文件的核心）

小数与金额一律整数分、计算用 Decimal、舍入 `ROUND_HALF_UP`；缺数据必须显示"缺口"，
不得显示假零。以下口径在页面、导出与提醒中必须一致，并固定展示口径说明。

### 4.1 收入

- 默认**按开票确认收入**：项目收入 = 该项目已开票金额（不含税；税率可选，默认不含税）。
- 未开票的合同额单列为**待开票**，不计入收入。
- 对不需要开票的客户，项目级可改为**按收款确认收入**（单选，历史不重算）；两种方式不并存。
- 不做：收入确认方法（固定价/服务期/累计计量）、履约配对、管理收入、收入追溯、税额成本调整。

### 4.2 成本

- **人工成本** = 已记录工时（分钟）× 成员内部成本费率（按业务日期快照）。
- **直接费用（含采购、外包）**：一条"项目支出"记录就是成本事实（项目、类别、金额、发生日期、
  供应商/说明、附件可选），确认后计入成本。付款是**同一支出下的付款记录**（付款日期、金额、账户，
  可 0–N 次），只有实际付款才计入现金。一笔支出可以一次付清、分次付款或尚未付款。
- **成本与现金必须分开记，但不需要拆成两张互不相干的单据**：成本按支出记录计一次；
  现金按该支出的实际付款累计计一次；成本不会因为付款再记一次，付款也不会另生成一笔成本。
- **未付金额** = 支出金额 − 已付款合计，必须进入未来 8 周现金计划（按预计付款日），
  不允许用"还没付钱"把已发生的成本藏起来，也不允许用"已确认成本"冒充已付现金。
- **先付款后取得服务/货物（预付）不设预付科目**：成本按发生/确认日期计，现金按实际付款日期计；
  同一笔业务不因付款时点不同而重复记账。
- 不做：采购订单/承诺、暂估转正式、跨期预付耗用、退货折让、税额抵扣、共享费用分摊/重分摊。

### 4.3 项目收益

- 项目毛利 = 收入 − 成本（人工成本 + 直接费用）；同时展示本期与累计。
- 收入为 0 时毛利率无定义；缺工时费率、缺费用确认、未开票等显示缺口与数量，不显示 0。
- 不做：预算版本、ETC/EAC、完工偏差、13 周经营预测、结项复盘。

### 4.4 现金流

- **项目现金净额** = 该项目已收款 − 已付款（每笔收付款必须可归属项目或"非项目"）。
- **公司现金余额** = 各账户余额之和（银行/支付宝/微信/现金账户，人工维护余额）。
- **未来 8 周计划** = 未收的合同收款计划 + 未付的付款计划 + 已确认但未付款的支出
  （按预计付款日）；付款后从计划转为实际现金，不重复计算；预计余额为负时提示缺口。
- 不做：银行流水导入与自动分类/对账、内部转账、手续费拆分、预收预付抵扣、多币种汇兑。

### 4.5 必须永远区分

已开票 ≠ 已收款；项目毛利 ≠ 项目现金净额；项目现金净额 ≠ 利润 ≠ 银行余额；
合同额 ≠ 收入；成本发生 ≠ 已付款。未付支出不是已付现金，也不是利润。
1.0 不提供法定总账、纳税申报、工资代发或对外财务报表。

## 7. 与现有实现的关系（复用与缺口）

**可直接复用的主干**（`core` 项目账已按项目归属）：

- 项目、任务/里程碑、工时与费率快照、费用、收款/付款、现金计划与现金预测、成本汇总、
  3 类 CSV 导入、台账/工时导出、审计、单层日期锁、`manage.py seed_demo` 演示数据。

**需要新增的最小能力**（当前代码不存在或口径不同）：

1. 项目收益：收入（开票/收款口径）与"收入 − 成本"毛利聚合与页面；现有"管理收入"不是利润。
2. 极简客户/合同/收款计划：现有 `Project.contract_cents` 只是立项历史值，正式合同在复杂插件里。
3. 极简开票/待开票：现有发票插件依赖合同/结算/税额资格且不写项目收入。
4. 项目收益 + 现金流一屏工作台：首页现只有成本/收付款/预测，无收入与毛利。
5. 项目级现金归属统一：core 项目账已可归属，但复杂插件的公司银行现金没有项目归属；
   1.0 明确用 core 项目账，不用公司银行账冒充项目现金流。
6. 简化导航与入口门控：10 个业务插件默认全开（`default_enabled: True`），需按本范围隐藏/停用，
   并处理不受插件启停门控的页面（如 `/finance/`、项目详情管理收入面板）。
7. 单人确认口径（免审批）与一键演示（`scripts/demo.py` 尚不存在）。

工程底线不变：9 项必需 CI、独立复核、PostgreSQL 多连接并发证据、金额/权限/审计反例测试、
覆盖率与测试数门禁不因简化而减少。

**视觉重设计**：前端整体视觉重设计（参考飞书设计系统）已按负责人要求暂停；本文件只定义页面范围，
入口收口由 Q-32 执行；整体视觉重设计在范围确认后由另行恢复的 UI 票据承担，不并入本队列。

## 8. 设计方案

设计目标：在现有代码上做"减法"而不是另起一套。复用 core 项目账与账本/审计能力，新增一个极简销售插件
承载客户/合同/发票，复杂插件默认停用并做入口门控；页面按 8 个入口组织，口径统一由服务层计算。

### 8.1 页面与导航（信息架构）

| 入口 | 页面（优先沿用现有路由） | 主要内容 | 可见角色 |
| --- | --- | --- | --- |
| 工作台 | `/`（重做内容，不新增路由） | 本月开票/收款/支出、现金余额、未收款合计、项目毛利排行、到期提醒 | 老板、项目经理 |
| 项目 | `/projects/`、`/projects/<id>/` | 项目列表；详情页：合同额→开票→收款→成本（工时/费用）→毛利→现金，可下钻明细 | 老板、项目经理；成员只读本人项目 |
| 客户与合同 | 新增 `/customers/`、`/contracts/`（精简插件） | 客户档案；每项目一个合同额、可追加金额变更、1–6 期收款计划 | 老板、项目经理（写）；成员不可见 |
| 工时 | `/time/`（沿用，去掉审批状态） | 周视图填报（项目/日期/分钟/说明）、更正；缺费率缺口清单 | 全部角色（成员仅本人） |

| 开票与收款 | 新增 `/billing/`（精简插件） | 发票登记（号码/金额/税率可选/日期/项目）；收款登记并归属项目/合同/发票；未收款 | 老板、项目经理 |
| 现金 | 新增 `/cash/`（复用 core 现金计划与账户） | 账户余额与流水；未来 8 周收款/付款计划与缺口 | 老板、项目经理 |
| 设置 | `/settings/`、`/audit/`（沿用；审计只读） | 成员与角色、成员成本费率、公司信息；审计日志 | 老板 |

不做同名替换以外的视觉重设计：页面样式沿用 `docs/engineering/ui-tokens.css` 与视觉规范；整体视觉重设计
按负责人要求另行暂停恢复，不在本方案内改视觉风格。

### 8.2 核心对象与关系

| 对象 | 来源 | 关键字段 | 规则 |
| --- | --- | --- | --- |
| Project | 复用 core | 客户、起止、负责人、状态 | 项目是全部数据的中心 |
| Customer | 新增精简插件 | 名称、联系人、备注 | 不做客户门户/供应商主数据 |
| Contract | 新增精简插件 | project、金额（分）、税率可选、起止、状态 | 每项目一个；改额追加变更记录（金额/原因/日期），历史金额只读 |
| PaymentPlan | 复用 core `CashPlan`（收款方向） | 到期日、金额（分）、状态 | 未收计划进入 8 周现金计划 |
| Timesheet / CostRate | 复用 core | 项目、成员、日期、分钟、说明；成员月度内部成本费率（生效日） | 工时直接生效（免审批）；成本=工时×费率快照 |
| Expense | 复用 core `Document(kind=expense)` | project、类别、金额（分）、发生日期、说明、附件 | 确认即成本；可更正 |
| ExpensePayment | 新增极简主从对象 | expense、账户、付款日期、金额（分） | 付款才计现金；Σ付款 ≤ 支出金额；未付进 8 周计划 |
| Receipt | 复用 core `Document(kind=receipt)` | 项目/合同/发票、账户、日期、金额 | 可部分；同一收款只消费一次 |
| Invoice | 新增精简插件 | project/contract、号码、金额（分）、税率可选、开票日期、状态 | 作废追加记录；默认收入口径 |
| Account | 复用/精简现有资金账户 | 名称、类型（银行/支付宝/微信/现金）、余额 | 余额人工维护；不做银行流水导入/对账 |
| LedgerEntry / 审计 | 复用 core | 成本/现金分录、来源、操作者 | 只追加；纠错负值冲销；不重算历史 |

关系：`Project 1–1 Contract 1–N PaymentPlan`；`Project 1–N Invoice 1–N Receipt`；
`Project 1–N Expense 1–N ExpensePayment`；`Project 1–N Timesheet`。
成本、现金、收入都落到 core `LedgerEntry`/只读聚合，不产生第二套账。

### 8.3 关键流程

1. **建客户→项目→合同**：客户与合同页新建客户；项目创建时选客户、填合同额与 1–6 期收款计划；
   合同金额后续变更用追加记录。
2. **记工时→人工成本**：成员周视图填报，保存即生效；系统按成员费率快照生成人工成本；
   缺费率进入缺口清单，不显示 0 成本。
3. **记费用/采购→成本与付款**：登记支出（含采购/外包）确认后计成本；付款时在同一支出下登记付款
   （可多次），付款才计现金；未付金额进入 8 周现金计划。
4. **开票→收款→未收款**：登记发票形成"已开票/待开票"；登记收款并归属项目/合同/发票（可部分），
   未收款 = 已开票 − 已收款；作废/退款用负值追加。
5. **看结果**：工作台看公司级收益与现金，项目页看合同额→开票→收款→成本→毛利→项目现金净额；
   所有页面固定展示口径说明，缺数据显示缺口。

### 8.5 复杂能力隐藏方案

- 复杂插件 `default_enabled=false`，由 owner 在设置中按需启用；停用后业务写拒绝、历史只读。
- 导航只保留 §8.1 的 8 个入口；直接访问复杂页返回 404/403 或引导回工作台，不以"菜单隐藏"代替门控。
- core 内嵌的插件面板（`/finance/`、项目详情"已确认管理收入"、人工成本池等）必须一并门控，
  不能只靠插件停用（这些页面不读插件启停状态）。
- 不删表、不删迁移、不删测试、不重算历史；新增迁移只追加。停用/拒绝访问留审计事件。
- 实现顺序先做 Q-32 门控 spike：验证停用依赖图（contracts 被多插件依赖）与页面可达性，再删入口。

### 8.6 权限与数据边界

- UI 只呈现 3 个角色：老板（全权）、项目经理（负责项目）、成员（本人投入 + 所属项目只读）；
  成本费率对成员隐藏；后端历史角色保留但不在小微版导航出现。
- 租户/项目/期间/状态/来源检查仍在服务层；跨租户、越权、超期、重复提交必须拒绝。
- 金额整数分、Decimal/`ROUND_HALF_UP`；账本与审计只追加；来源唯一消费；锁期拒绝路径保留。
- 导出仅授权范围并留审计；不含个人费率/工资。

### 8.7 技术约束与不变量

- Django/DRF/templates，不引入前端构建链；复用现有视觉令牌与页面模式。
- SQLite 开发、PostgreSQL 生产；迁移只新增；并发正确性只认 PostgreSQL 多连接证据。
- 新增业务对象进独立插件 App，不把合同/结算等对象塞回 core；core 只加必要的只读聚合。
- 9 项必需 CI、独立复核、覆盖率与测试数门禁不变；每个 PR 代码 ≤约 300 行、自带浏览器/命令演示。

### 8.8 取舍与备选

- **新精简插件 vs 复用复杂 contracts/invoicing**：选择新精简插件，避免改复杂插件的历史/审批语义；
  复杂插件保留只读。
- **支出单+付款记录 vs 两套独立单据**：选择主从记录——成本事实与现金事实必须分开，但用户只录一次支出，
  避免重复记账与"付款再记成本"。
- **收入按开票 vs 按收款**：默认开票可项目级切换，都是简单口径；不做收入确认方法。
- **8 周 vs 13 周预测**：复用 core 13 周预测计算，页面只展示未来 8 周，减少用户认知负担。
- **默认免审批**：一人公司可用性优先；保留审计，未来恢复审批时自审阻断不放宽（D-11）。

## 10. 1.0 发布标准（小微版）

- **端到端**：真实浏览器一次走通 客户→项目→合同→工时→费用→开票→收款→看收益/现金，
  1440/390 两档 + 键盘可用 + 空/错/载/停四态。
- **质量**：9 项必需状态检查全绿；一次独立复核作用于当前 HEAD；金额/权限/审计反例测试与
  `verify_integrity` 通过；PostgreSQL 并发证据存在。
- **运维**：干净环境按文档安装可重试；数据库与附件备份→隔离恢复实测一次，恢复后数字一致。
- **演示**：一条命令得到演练环境、账号与 5 步演示脚本，重复执行幂等，数据不含真实客户/工资/凭据。
- **记录**：ACCEPTANCE 逐项真实结果，`not_run` 不写 `pass`；候选包可核对。
- **不要求**（从发布前置降级）：客户 UAT 三模板、三方签批、TLS 深度验收、性能基线、
  旧库升级、期初承接；这些在对外试点前按需补。
- **版本**：先出 `0.2.x` 预发布候选，达到上述标准后再评 1.0（2026-11-03 已确认，D-11）。

## 11. 影响与风险

- 代码：复杂能力保留但默认停用/隐藏，短期维护成本仍在（测试与迁移继续跑）；后续专业版可恢复。
- 数据：无删除、无重算；历史账与审计只追加可读；新公司从启用日开始，不承接历史。
- 文档：原 [product-requirements.md](product-requirements.md) 降为该简化版之下的完整规则参考；
  QUEUE 重排为小微版队列，旧专业版队列归档只读。
- 风险：入口隐藏不彻底（直接 URL 可达，需 Q-32 门控 spike 验证）；数据双栈（core 项目账与插件栈
  不互通，本方案只承诺 core 口径）；"开票=收入"与实际财务认知差异（项目级可切按收款）；
  免审批口径已确认但恢复审批时不得放宽自审阻断；未删代码的维护成本。
- 未验证：本文件是范围/设计定义，不含代码/迁移/数据改动；实现与浏览器证据见 QUEUE W1–W3。
