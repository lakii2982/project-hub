# 产品范围：小微企业简化版（项目收益与现金流）

状态：2026-11-03 起生效。本文件是 1.0 产品范围的唯一定义；执行顺序见
[../project/QUEUE.md](../project/QUEUE.md)，现状见 [../project/STATUS.md](../project/STATUS.md)，
已定决定与待确认项见 [../project/DECISIONS.md](../project/DECISIONS.md)。

## 1. 为什么重定义

原 1.0 按"专业项目财务系统"设计：合同版本与审批、客户验收/服务期收入确认、应收应付与核销、
预算版本/ETC/EAC、四类核对、月度锁账关期、多币种、工资社保个税。它面向有专职财务的团队，
对小微企业认知负担过高。

2026-11-03 产品负责人判断：面向小微企业的版本太重，用户搞不清复杂财务知识，只想算明白
**项目收益和现金流**，要求简化功能并重新定义产品范围。据此作以下决定（DECISIONS D-09）：

- 1.0 = **小微企业简化版**：以项目为中心，回答"项目赚了多少、钱收回来没有、现金够不够"。
- 专业财务能力移出当前 1.0，代码与数据保留、默认隐藏/停用，后续按需启用（不是删除）。
- 简化的只是产品界面与流程，**不是资金正确性**：金额整数分、Decimal/`ROUND_HALF_UP`、权限与
  租户隔离、审计只追加、来源唯一消费、期间/锁期拒绝路径等底线不变（见 AGENTS.md）。

## 2. 目标用户与要回答的问题

- 目标用户：5–50 人（上限 100 人以下）的软件开发、实施与技术服务公司；老板兼经营决策、可能兼财务；
  没有专职财务、没有 ERP/OA；用浏览器使用自托管实例。
- 老板每周只关心三个问题：
  1. **这个项目赚了多少？** 项目收益（收入 − 成本）
  2. **钱收回来没有？** 已开票、已收款、未收款
  3. **现金够不够？** 现金余额、未来 8 周预计收款与付款缺口
- 一句话定义：用项目串起合同、工时与费用、开票与收款，让老板每周 5 分钟看清项目赚没赚、
  钱回没回、现金够不够。

## 3. 核心链路（1.0 必须端到端可用）

```text
客户 → 项目 → 合同额/收款计划 → 工时与费用 → 开票 → 收款 → 项目收益 + 现金流
```

| # | 用户动作 | 系统结果 | 入口 |
| --- | --- | --- | --- |
| 1 | 建客户、项目、合同额与收款计划 | 项目有合同额、客户、起止与收款节点 | 客户与合同 / 项目 |
| 2 | 成员按周填工时；老板/PM 登记费用或外包支出 | 项目人工成本与直接费用自动汇总 | 工时 / 费用 |
| 3 | 登记一张发票（号码、金额、日期、项目） | 已开票、待开票、未收款发生变化 | 开票与收款 |
| 4 | 登记一笔收款（账户、金额、日期、客户/项目） | 项目现金净额与账户余额发生变化 | 开票与收款 / 现金 |
| 5 | 打开工作台与项目页 | 一屏看到项目收益、未收款、现金与缺口 | 工作台 / 项目 |

## 4. 简化后的计算口径（本文件的核心）

小数与金额一律整数分、计算用 Decimal、舍入 `ROUND_HALF_UP`；缺数据必须显示"缺口"，
不得显示假零。以下口径在页面、导出与提醒中必须一致，并固定展示口径说明。

### 4.1 收入

- 默认**按开票确认收入**：项目收入 = 该项目已开票金额（不含税；税率可选，默认不含税）。
- 未开票的合同额单列为**待开票**，不计入收入。
- 对不需要开票的客户，项目级可改为**按收款确认收入**（单选，历史不重算）；两种方式不并存。
- 不做：收入确认方法（固定价/服务期/累计计量）、履约配对、管理收入、收入追溯、税额成本调整。

### 4.2 成本

- **人工成本** = 已记录工时（分钟）× 成员内部成本费率（按业务日期快照）。
- **直接费用（含采购、外包）**：一条"项目支出"记录就是成本事实（项目、类别、金额、发生日期、
  供应商/说明、附件可选），确认后计入成本。付款是**同一支出下的付款记录**（付款日期、金额、账户，
  可 0–N 次），只有实际付款才计入现金。一笔支出可以一次付清、分次付款或尚未付款。
- **成本与现金必须分开记，但不需要拆成两张互不相干的单据**：成本按支出记录计一次；
  现金按该支出的实际付款累计计一次；成本不会因为付款再记一次，付款也不会另生成一笔成本。
- **未付金额** = 支出金额 − 已付款合计，必须进入未来 8 周现金计划（按预计付款日），
  不允许用"还没付钱"把已发生的成本藏起来，也不允许用"已确认成本"冒充已付现金。
- **先付款后取得服务/货物（预付）不设预付科目**：成本按发生/确认日期计，现金按实际付款日期计；
  同一笔业务不因付款时点不同而重复记账。
- 不做：采购订单/承诺、暂估转正式、跨期预付耗用、退货折让、税额抵扣、共享费用分摊/重分摊。

### 4.3 项目收益

- 项目毛利 = 收入 − 成本（人工成本 + 直接费用）；同时展示本期与累计。
- 收入为 0 时毛利率无定义；缺工时费率、缺费用确认、未开票等显示缺口与数量，不显示 0。
- 不做：预算版本、ETC/EAC、完工偏差、13 周经营预测、结项复盘。

### 4.4 现金流

- **项目现金净额** = 该项目已收款 − 已付款（每笔收付款必须可归属项目或"非项目"）。
- **公司现金余额** = 各账户余额之和（银行/支付宝/微信/现金账户，人工维护余额）。
- **未来 8 周计划** = 未收的合同收款计划 + 未付的付款计划 + 已确认但未付款的支出
  （按预计付款日）；付款后从计划转为实际现金，不重复计算；预计余额为负时提示缺口。
- 不做：银行流水导入与自动分类/对账、内部转账、手续费拆分、预收预付抵扣、多币种汇兑。

### 4.5 必须永远区分

已开票 ≠ 已收款；项目毛利 ≠ 项目现金净额；项目现金净额 ≠ 利润 ≠ 银行余额；
合同额 ≠ 收入；成本发生 ≠ 已付款。未付支出不是已付现金，也不是利润。
1.0 不提供法定总账、纳税申报、工资代发或对外财务报表。

## 7. 与现有实现的关系（复用与缺口）

**可直接复用的主干**（`core` 项目账已按项目归属）：

- 项目、任务/里程碑、工时与费率快照、费用、收款/付款、现金计划与现金预测、成本汇总、
  3 类 CSV 导入、台账/工时导出、审计、单层日期锁、`manage.py seed_demo` 演示数据。

**需要新增的最小能力**（当前代码不存在或口径不同）：

1. 项目收益：收入（开票/收款口径）与"收入 − 成本"毛利聚合与页面；现有"管理收入"不是利润。
2. 极简客户/合同/收款计划：现有 `Project.contract_cents` 只是立项历史值，正式合同在复杂插件里。
3. 极简开票/待开票：现有发票插件依赖合同/结算/税额资格且不写项目收入。
4. 项目收益 + 现金流一屏工作台：首页现只有成本/收付款/预测，无收入与毛利。
5. 项目级现金归属统一：core 项目账已可归属，但复杂插件的公司银行现金没有项目归属；
   1.0 明确用 core 项目账，不用公司银行账冒充项目现金流。
6. 简化导航与入口门控：10 个业务插件默认全开（`default_enabled: True`），需按本范围隐藏/停用，
   并处理不受插件启停门控的页面（如 `/finance/`、项目详情管理收入面板）。
7. 单人确认口径（免审批）与一键演示（`scripts/demo.py` 尚不存在）。

工程底线不变：9 项必需 CI、独立复核、PostgreSQL 多连接并发证据、金额/权限/审计反例测试、
覆盖率与测试数门禁不因简化而减少。

**视觉重设计**：前端整体视觉重设计（参考飞书设计系统）已按负责人要求暂停；本文件只定义页面范围，
入口收口由 Q-32 执行；整体视觉重设计在范围确认后由另行恢复的 UI 票据承担，不并入本队列。

## 8. 1.0 发布标准（小微版）

- **端到端**：真实浏览器一次走通 客户→项目→合同→工时→费用→开票→收款→看收益/现金，
  1440/390 两档 + 键盘可用 + 空/错/载/停四态。
- **质量**：9 项必需状态检查全绿；一次独立复核作用于当前 HEAD；金额/权限/审计反例测试与
  `verify_integrity` 通过；PostgreSQL 并发证据存在。
- **运维**：干净环境按文档安装可重试；数据库与附件备份→隔离恢复实测一次，恢复后数字一致。
- **演示**：一条命令得到演练环境、账号与 5 步演示脚本，重复执行幂等，数据不含真实客户/工资/凭据。
- **记录**：ACCEPTANCE 逐项真实结果，`not_run` 不写 `pass`；候选包可核对。
- **不要求**（从发布前置降级）：客户 UAT 三模板、三方签批、TLS 深度验收、性能基线、
  旧库升级、期初承接；这些在对外试点前按需补。
- **版本**：先出 `0.2.x` 预发布候选，达到上述标准后再评 1.0（版本命名见 P-04）。

  尚需新事实；一人公司免审批口径需确认；范围确认前按旧队列开工。
