# 部署、维护与恢复

更新日期：2026-10-27。当前为工程验证版的运维路径；Docker与PostgreSQL命令需要在实际目标环境执行并留存结果。

## 环境和身份

- 本地：Python 3.12+、SQLite，仅监听127.0.0.1。生产：Docker Compose、PostgreSQL17、Caddy TLS、Gunicorn。
- `.env`独立保存，不提交版本库。服务器只开放80/443和受限管理通道，数据库与应用端口不对公网开放。
- 应用密钥至少40字符、数据库密码至少16字符，分别随机生成。修改应用密钥会使个人接入失效，需要重新授权；用户修改密码也会撤销其旧PAT的有效性。
- 公司负责人开通账户，人员离职先停用用户/成员并撤销其PAT，历史记录保留。当前可通过管理命令或受控Django shell停用；完整成员停用UI列在工作单。
- 管理员重置密码：`docker compose exec app python manage.py changepassword 用户名`，交互输入，不通过命令参数传密码。

本机演练环境与登录信息位置见[本地测试环境](local-testing.md)。此处服务器部署步骤仍需在目标环境执行，不与本机演练混用。

## 首次启动与检查

1. 填写`.env`，配置域名DNS，执行`docker compose up -d --build`。
2. `docker compose logs --tail=100 app`检查迁移与启动结果；不要把含环境秘密的完整诊断转发到聊天。
3. `docker compose exec app python manage.py check --deploy`；通过HTTPS访问`/health/`，应返回status=ok。
4. 交互运行`bootstrap`，通过浏览器录入最少人员、实际审批人、成本费率、首个项目和现金计划。
5. 执行`docker compose exec app python manage.py verify_integrity --json`。
6. 在隔离测试数据上完成工时→审批→成本、费用→审批、实际收付→核销、冲销、锁账和跨身份访问检查。

不得把演练数据初始化到生产数据库。`check --deploy`是配置检查，不能代替生产流程与权限验证。

## 日常运维

- 每日检查应用/数据库健康、磁盘、失败登录、异常投递积压、待审批/缺费率与逾期计划；每天执行完整性校验。
- 清理过期会话：`python manage.py clearsessions`。个人令牌过期后认证自动拒绝，按保留策略留审计，不直接删除历史事件。
- 规则与财务计算无需模型连接。模型故障只影响草稿提取，不回退到未经校验的结果、不自动重复计费调用。
- 插件事件使用事务内Outbox。消费入口与插件配置见插件手册；事件失败不会回滚已提交账目，失败需定位并按相同事件ID重试。
- 日志不记录Authorization、原始令牌、密码、模型密钥或完整业务输入。API响应包含X-Request-ID，供定位对应审计事件。

## 一致性备份

在项目目录执行：

```sh
sh scripts/backup.sh
```

脚本短暂停原本运行的app/worker，保持数据库运行，导出数据库与附件，再恢复这些服务的原状态。已存在的输出目录会被拒绝，不覆盖旧备份。目录/文件权限为0700/0600；失败返回非零并保留 `.incomplete`，有此标记的目录不能当作成功备份。成功包包括数据库custom dump、附件归档、内容清单和相对路径SHA256；在备份目录内用 `sha256sum -c SHA256SUMS`（macOS用 `shasum -a 256 -c SHA256SUMS`）校验。`.env`独立安全保管。检查退出状态后，将成功备份复制到另一台受控设备或加密存储。同机磁盘副本不足以覆盖机器故障。

建议初始恢复目标：RPO不超过24小时、RTO不超过4小时。它们是待演练的目标，不是已证明的服务承诺。依据项目数据量和变更频率调整。

## 隔离恢复演练

1. 新建隔离Compose项目和空数据库/附件卷，使用匹配版本的源码与依赖锁。不得覆盖现有生产卷。
2. 校验数据库与附件SHA256，`pg_restore --list`检查结构；用`pg_restore --exit-on-error --no-owner`导入**空库**。迁移创建的追加限制触发器会随dump恢复。
3. 解压附件到隔离的runtime卷，保持目录结构和应用用户读写权限。不要将未知归档解压到宿主机根目录。
4. 用测试域名启动应用，校验`verify_integrity`、历史账目合计、审批与审计链、附件打开和sha256。
5. 记录恢复时长、备份时间点、数据缺口与失败项；演练成功后才把该路径作为生产恢复依据。

GitHub CI已执行真实pg_dump、SHA256校验及隔离新PG库restore/integrity，最近产品证据见PR#52运行40486300463。该链路尚未证明真实生产环境、非空附件恢复后的凭证浏览/报表一致性或恢复时长目标；目标服务器仍需按上述步骤演练。

## 升级与回退

1. 阅读版本差异与迁移说明，在生产副本跑迁移、业务测试和恢复演练。
2. 升级前做一致性备份并记录源码包SHA256与依赖锁。
3. 插件先检查内核API、依赖版本、权限变化、迁移兼容和未完成事件；停用不删除数据。
4. 数据库变更采用先扩展、迁移、再收缩；旧版本须能读扩展后的结构，财务来源与账本只追加。
5. 仅应用代码变化可回退到兼容镜像；发生不可逆结构/数据迁移时，用事先验证的整库与附件恢复路径，不运行未经验证的反向迁移。

不要为兼容新插件而关闭账本/审计不可变约束。第三方插件代码需审查，未受信代码放入隔离服务，通过窄范围API访问。
