# 1.0 跨模块契约、原子写入与升级设计

状态：目标契约设计候选。由后续PRE-CONTRACTS准备包展开字段级schema、状态/权限矩阵及契约测试，经规划冻结后才成为实现依据。不是当前SDK已实现的能力。对象所有权承接[交付方案第4章](../v1.0-delivery-plan.md)，不另立同名权威。

## 1. 契约目录与版本规则

| 契约ID | 所有者与内容 | 主要消费者 | 必须冻结的具体产物 |
| --- | --- | --- | --- |
| C01 身份与命令上下文 | 共享授权：组织、当前成员、项目/池、角色/字段权限 | 全部写/读服务 | 身份来源、权限矩阵、错误隐藏策略；不接受客户端自报角色/actor |
| C02 SourceRef与核算事件 | 内核：稳定业务来源、事件类型、幂等/冲销/审计/Outbox接口 | 全部核算域、导入、旧接口适配 | 来源命名空间、唯一键、版本、事件/凭证配对及引用schema |
| C03 员工/项目/往来方查询 | 现有masterdata、contracts往来方子域 | 合同、投入、成本、结算、现金、发票 | 稳定ID、有效日期、停用/合并、个人字段遮蔽、Employee收付引用 |
| C04 合同与方法政策 | contracts：有效明细、上限、收入/结算方法、批准变化 | delivery、settlement、revenue、planning | 含税拆分、方法选择版本、累计消费与终止/负调整约束 |
| C05 履约与投入 | delivery/time：验收、服务期确认、实际分钟和可计费确认 | costing、settlement、revenue | 来源范围、单位、部分引用、变更及同服务互斥覆盖 |
| C06 成本与支出来源 | costing：工资/费用池、承诺、已发生、税额、分配 | settlement、cash、planning、reconciliation | 原额/去向守恒、费用/付款区分、暂估/实际升级、取整组及版本 |
| C07 义务与核销 | settlement：结算、OpenItem、核销/抵扣、信用更正 | cash编排、invoicing、revenue配对、insights | 往来方/项目约束、未清额、SourceRef资金证明、可核上限/反向关系 |
| C08 现金与资金可用额 | cash：交易、归属、预收预付/退款、实际日期 | 核销编排、reconciliation、forecast | 银行源唯一、资金可用额、部分归属、内部互转和退回语义 |
| C09 发票/履约结算配对 | invoicing拥有票据分配；revenue拥有履约结算配对 | 核对、insights | 税额与金额上限、红冲、配对更正及不得重复确认 |
| C10 预算/剩余/预测覆盖 | costing/planning与cash各拥有其预计事实 | 统一insights/导出 | AC/ETC互斥、现金来源升级的部分覆盖与余量、基准日/情景 |
| C11 期间与期初 | 内核期间接口＋各域专用期初命令 | 全部写服务、onboarding、close | 业务日/入账期、锁序、覆盖区间、累计/当期、锁后调整 |
| C12 读模型与证据 | insights统一指标；交付层拥有验收回执 | 页面、导出、受权API、发布 | null/缺项/权限/水位、指标名称、来源穿透和候选绑定 |

契约清单必须为每项确定：命令/查询/事件的稳定名称及版本、请求/返回JSON schema、错误码、必填/可空、枚举、默认值、精度、权限、来源/幂等、前置版本、事务/锁、迁移/兼容和生产者/消费者测试。新的方法/状态/字段不能仅由某个UI先约定。

兼容：只读新增可选字段可向后兼容，但消费者必须按schema明确处理；新增必填字段、金额/日期语义、状态迁移或默认值改变均不是“加字段无影响”。未知写字段拒绝；缺值与0区分；金额/分钟严格整数且拒绝bool/float。枚举新增需要消费者未知值测试；不允许消费者将未知财务状态映射成成功。弃用提供适配和期限，首版至少保留冻结基线声明支持的入口直到升级验收完成。

## 2. 统一命令与查询包络（设计）

```json
{
  "contract": "settlement.clearance.create/v1",
  "request_id": "opaque-unique-id",
  "idempotency_key": "bounded-client-key",
  "expected_version": 3,
  "occurred_on": "2026-10-27",
  "posting_period": "2026-10",
  "source": {
    "kind": "cash.transaction",
    "id": "stable-id",
    "version": 1
  },
  "payload": {
    "open_item_id": "stable-id",
    "amount_cents": 10000
  }
}
```

例子说明字段角色，不是可直接派遣/对外调用的现有端点。组织、actor、授权项目由服务器会话/PAT及服务上下文推导，不能相信payload传来的身份；实际schema按命令定义适用字段，非所有命令强行带金额/来源。幂等键只在声明的组织＋命令/客户端命名空间内使用，规范化输入摘要含版本和有效业务参数；同键同内容返回已有业务结果，同键改内容冲突。实际业务来源唯一键独立保护跨UI/导入/API重复，不可仅依靠请求key。

统一结果：稳定对象ID、当前业务版本、结果类型（created/existing/dry_run）、发生的事件ID、可回查的来源和必要遮蔽数据；结果类型不代替业务审批状态。写入dry_run沿现有语义整体回滚业务、核算、Outbox及操作记录，不把试算结果当生效凭证。安全认证/限流/安全日志按既有独立策略处理，不能把试算当隐身通道。

错误语义至少区分：validation_error、permission_denied/not_found（按端点存在性隐藏契约）、version_conflict、idempotency_conflict、period_locked、dependency_disabled、source_already_consumed、insufficient_available、policy_unconfirmed、missing_evidence、transient_database_failure。客户端只展示可读原因与办理路径，不泄露其他租户或个人费率。事务未知结果先按请求/来源查询对账，再决定重试，不能直接再提交新key。

查询必须先授权再汇总，基准日包含性/业务日或入账期/币种/范围/有效调整明确；分页采用固定稳定排序，不通过翻页重复/漏计改变汇总。时间戳保存UTC，业务日期按企业Asia/Shanghai解释，期间独立保存；截止日和午夜边界有测试。

## 3. 原子写入与全局锁序

**沿既有架构先锁公司，不能新增期间先于公司锁的反向路径。** 同公司业务串行是首版明确取舍；不在未测性能前擅自拆细锁。

统一序列：身份解析与输入清洗 → 开事务 → company行锁 → 锁内重查身份/项目/期间/启用状态 → 如适用按稳定顺序锁period/项目 → 资源按固定类型顺序及ID升序（来源、现金交易、未清项、分配） → 业务约束/幂等/来源唯一检查 → 领域写/账本/核销关系/审计/Outbox → 提交。具体表/类型排序由C02/C07/C08/C11共同冻结，所有调用者遵循同一清单，不能每个域自己选。

公司锁、数据库唯一约束与实体expected_version各有作用：公司锁保护同租户串行，唯一键兜底跨入口重复，业务版本给用户可理解的过期冲突。SQLite不支持SELECT FOR UPDATE，不能证明该设计的生产竞争正确。

| 动作 | 唯一事务入口/所有者 | 同步原子更新 | 失败后条件 |
| --- | --- | --- | --- |
| 工时过账/重算调整 | costing应用服务，调用time授权查询和内核 | 来源消费、成本事件、分配、审计 | 无半笔人工成本；旧分币值不变 |
| 费用/验收确认与应付 | 成本侧编排调用costing和settlement命令 | 发生事实、成本、应付来源/未清、承诺释放、审计 | 不允许成本有了而义务失踪；契约说明不适用应付的来源 |
| 收付款核销/预收抵扣 | cash应用编排；settlement唯一登记核销 | 资金来源/可用额证明、核销/抵扣、未清派生、审计 | 无重复现金；双方余额在同一事务可核对 |
| 退款/银行退回 | cash编排，按业务类型引用settlement/成本/收入更正 | 可退检查、反向现金、必要核销恢复/更正、审计 | 不能恢复两次未清；退款与信用更正分清 |
| 共享/工资分配 | costing | 源可分范围、分配运行/去向、分币事件、审计 | 源与去向守恒；公司层不双计 |
| 收入/结算配对 | revenue侧编排查询合同、履约、settlement | 累计收入差额、配对/未履约/未结算范围、审计 | 结算不第二次确认收入，方法版本明确 |
| 期初提交 | onboarding调用各域期初命令 | 覆盖清单、期初事件、未清/资金、审计 | 已声明批次全有或全无；不因分块留下正式半账 |
| 锁账 | 期间应用服务 | 公司锁下预检、事件清单/快照、截止期、审计 | 竞争写要么先完成并被检查，要么锁后拒绝 |

同事务内跨域服务不得私自commit、开第二数据库或捕获异常后继续保存另一半。Outbox和通知不会“稍后补齐余额”。提交后通知失败只重试通知，不重放核算命令。死锁/序列化异常须整体回滚、有限重试原幂等请求；是否重试及上限写入固定命令契约，不能无限循环。网络提交结果未知以持久幂等结果对账。

## 4. 桥表和覆盖关系的唯一所有者

| 关系 | 所有者 | 上限和撤销/更正 |
| --- | --- | --- |
| 工时→客户确认计费范围 | time | 不重录投入；客户确认与成本分钟分别保留 |
| 来源成本→项目/非项目去向 | costing | 去向总额守恒；重分摊先反向旧运行，锁期开放期调整 |
| 现金/预收预付→未清项 | settlement | 同源可用/未清上限，cash编排验证双方，撤核不等于退款 |
| 银行交易→项目/非项目归属 | cash | 所有归属合计不超银行源，不能制造额外现金 |
| 发票→结算/费用 | invoicing | 含税/不含税/税额分别守恒，红冲不删除原事实 |
| 履约→已结算/未结算覆盖 | management_revenue | 同合同明细范围互斥，配对不增加第二份收入 |
| 现金计划→正式未清/实际覆盖 | cash预测来源子域 | 支持部分升级与残余，同一覆盖不得同时落多层 |
| 期初汇总→历史明细覆盖范围 | 各域期初记录＋统一批次编排 | 同项目/类别/期间互斥；只备查明细不再次过账 |

每种桥表须冻结typed SourceRef、组织、项目/池、对手、金额/数量范围、状态、版本、原/反向关系、唯一键和审计；不是任意JSON里放一个ID就视为跨域约束成立。

## 5. 旧新升级/切换清单

| 旧入口/对象 | 新目标与适配方式 | 切换前必须比对 | 禁止的快捷做法 |
| --- | --- | --- | --- |
| Project主档与contract_cents | Project ID保留，正式合同额切换为批准合同读模型；旧字段只作有来源历史/只读适配 | 旧合同占位与正式合同映射、批准版本、项目汇总 | 长期双写两个可编辑合同总额 |
| Employee/CostRate | 继续唯一员工ID；旧费率及业务日期规则保留，新成本政策/快照显式版本切换 | 历史工时成本逐分不变，员工/账号映射、无账号人员 | 当前工资覆盖旧费率、同名自动合并 |
| Timesheet及历史task_id | 旧表/主键先保留，time服务接管命令，旧UI/CSV/API/MCP转发 | 幂等、本人身份、分钟、已批状态、历史cost及task兼容 | 强制历史补任务或无迁移重算已入账成本 |
| Task/CashPlan关联 | 旧core外键/迁移留原处，SDK来源查询适配；新交付逻辑不反向import现金App | 节点校验、关闭项目、关键任务/历史区、禁用场景 | 搬表制造循环依赖或悄悄丢原关联 |
| Document费用/收付/预算/变更 | 按类型映射目标域及SourceRef；旧路由仅转发唯一命令 | 同来源只消费一次、原审批/证据/账本引用、税额与锁期 | 把旧预算变更直接当合同变更、复制费用再过账 |
| CashPlan与既有核销 | 仍为计划/历史记录，正式未清须逐来源批准承接；覆盖关系逐项映射 | 剩余计划/实际/新未清与预测互斥、预收抵扣、逾期 | 全额批量转应收、按同金额盲匹配 |
| LedgerEntry/AuditEvent | 保留账本行、主键、触发器和链；新事件用支持的内核接口追加 | 旧行逐字节/逐分、来源/反向链、整链与报表 | 拷贝后丢原主键、关闭触发器、覆盖余额 |
| API/CSV/MCP和浏览器URL | 已声明兼容版本转同业务服务，范围外新端点先冻结 | 同样输入/权限/幂等/金额和错误，dry_run不生效 | UI一套算法、旧导入另一套、隐藏入口代替门控 |

切换runbook固定：隔离合成旧库快照→检查原始完整性/哈希→应用新增迁移→建立可审阅映射和覆盖→只读新旧逐来源比对→停止该范围新写并排空确认中的请求→备份DB/附件→切换唯一写路由→冒烟/完整性/报表/权限→恢复业务。首版采用维护窗口，不追求双写零停机。

回填有批次ID、输入清单、覆盖范围、前后金额/行数/哈希、异常及人工批准；重跑幂等。回退只用与新结构兼容代码或经演练的隔离恢复，不倒放账本；不确认兼容时保持只读、保留新事实后制订前向修复。适配器移除须有明确兼容期限、调用审计及新旧UAT通过，不能因新UI可用就删除。

## 6. 契约变更与下游影响

契约owner提出新版本→列生产者/消费者和数据/测试影响→独立规划冻结→更新PH依赖及适配→生产者和消费者契约测试→旧/新夹具比较→串行迁移/接线→相关verify/review/CI/现场证据失效重验。工作包JSON的 `contracts` 与 `depends_on` 提供影响索引，不能假装它已自动执行此流程。

涉及新字段、权限、核算、外部API或数据迁移按现有S级规则；不能通过同时修改本实现PR的schema和白名单给自己授权。新业务schema/文件清单尚未冻结时，允许继续其准备包，禁止开始它的业务实现。
