# 1.0 长程任务执行协议（设计）

依托[生命周期](../engineering/lifecycle.md)、[代理协议](../engineering/agent-protocol.md)、[失败恢复](../engineering/recovery.md)、[现有执行器](../engineering/local-team.md)与[交付门禁](../engineering/ai-delivery-delivery.md)。这些是既有约束，本文件只补1.0的执行安排，不改变其权限或实现。

## 1. 权威来源与授权范围

| 事实 | 唯一权威 | 说明 |
| --- | --- | --- |
| 产品范围/业务政策 | 已批准产品规格及决策记录 | 本目录候选不自动变成批准政策 |
| 可执行任务、白名单、验收、状态 | 可信BASE上的project/tasks.json及其spec | Issue/聊天/工作包JSON不产生ready权限 |
| 已实现内容 | Git提交/差异与delivery-status | 规划和执行者自述不能代替源码 |
| 运行状态、进程和尝试 | 既有私有RunStore及执行器回执 | 不把UI显示“完成”视为进程已退出 |
| 验证/审阅 | 绑定最终候选的真实命令和独立回执 | 见验收设计，不继承旧PASS |
| 远端合入 | PR当前head、最新BASE、实时保护/检查/讨论 | 本机绿不等于能合并 |
| 正式发布和客户完成 | 同提交发行证据、现场记录和客户验收 | main合入不等于发布，研发完成不等于客户签收 |

未来一次长程实施授权应写清：允许的仓库、目标需求、规划/实施/PR/正常合入范围、候选环境、发布/部署和客户数据权限。已确认范围内不反复问；当前仍是准备设计授权，不推断已获恢复开发、生产部署或外部客户联络授权。普通技术选择由主控；业务口径冲突、客户真实数据/环境缺失才形成具体待决策项。

## 2. 单包派遣前检查

1. 固定可信BASE SHA、PH任务/spec摘要、工作包和需求ID；核对用户冻结/恢复指令。
2. 依赖均已交付且实际接口版本匹配；包相关政策通过冻结、客户参数在合成夹具中明确。
3. 原工作树脏修改归属明确。使用隔离分支/worktree，执行者只能写授权白名单子集。
4. 只交付必要源码、契约、失败反例和合成数据；移除凭据、客户身份、真实工资、历史全对话。
5. 执行器和备选能力有实际结果；指定时间/日志上限、执行次数、输出格式和取消/回收方式。
6. 固定复核者独立身份/上下文；为共享接线和迁移留主控范围。

不得把演练模板中的工作包ID直接交给现有控制器冒充PH ID。正式派遣使用 `projectctl brief <PH>` 和现有入口；未promote包停在设计层。

## 3. 文件所有权与集成

- 领域服务、域内模板/测试由对应执行者负责；另一个包不能因“都是同一功能”顺手修改。
- `pmo/urls.py`、`pmo/settings.py`、主导航、既有core共享入口、共同指标接线、完整性命令和治理元数据由主控单写。若包确需修改共享文件，正式spec必须显式分出集成子范围；执行者只提供补丁建议/接口说明。
- 同一文件的不同函数也视为范围冲突，除非已有可靠隔离合件协议证明互斥；首版保守串行。
- 迁移由主控按当前叶节点生成和串行集成，执行者交模型/数据迁移设计而不抢号。跨域迁移图在合入前检查。
- 完成工作区改动后先验收、独立复核，再由主控合件和共享接线；**合件后再次验收/复核最终差异**，此前子包结果只是输入证据。

## 4. 包状态和晋级

不新增一套可编辑任务状态机：设计包保持 `design_candidate`，正式范围映射到PH。PH只使用当前schema支持的状态；运行的queued/running/cancelled/unknown等沿既有RunStore。代码和文档不得伪装这些新状态已被projectctl支持。

派遣 → 实现返回 → 整理最终报告/交接 → 隔离验收 → 独立审阅 → 主控提交PR → 当前CI → 授权合入 → 主线完整性与追踪核对。任一步缺失均不done。一个包可拆多个PH；只有全部关联PH及集成验收完成才覆盖该包需求。

## 5. 证据冻结及失效

每次证据至少关联：PH、run/source_run、可信base_sha、contract_digest、候选diff_digest、执行器/复核者、命令/退出码/日志摘要、数据库和夹具版本、环境限制。远端阶段再关联PR/head、CI run、merge SHA。字段适用性遵循现有工具，不把新增字段强塞进未更新的schema。

源文件/测试/spec/接线/BASE改变使旧verify和review失效；更新后按现有gate重新绑定。复核发现补丁亦是新候选，不能把旧review PASS用于新代码。验收环境、数据库或关键夹具变化也要重跑相关证据。

公共report/handoff在最终验收前整理；验证回执保存在既有私有证据存储，不要求文件写入自身最终commit/diff摘要造成自引用循环。公共报告可引用run及证据标识；提交后的PR head绑定在外部回执/CI，不为补写“当前SHA”反复改当前提交。此安排复用现有gate，若工具尚不能处理某种证据，登记工具任务后验证，不绕开检查。

文档更正同样按现有gate规定处理摘要；不能以“不影响代码”为由悄悄复用不匹配回执。具体重验粒度受可信BASE验收契约约束，不能临场删减。

## 6. 中断、接续与接管

每次上下文切换、暂停、失败接管或合入后留下检查点：当前PH/run、BASE与候选、PR/CI状态、未提交文件及归属、政策/接口版本、已跑/未跑检查、失败签名、活进程与下个合法动作。检查点进入既有report/handoff或运行存储，禁止只留聊天。

恢复顺序：

1. 读用户最新指令和当前AGENTS，核对Git脏修改、HEAD/远端事实。
2. 从manifest/tasks活动交接定位任务，核对固定BASE/spec。
3. 查run进程身份、锁和取消状态；unknown/仍在写时不派新写者抢同一范围。
4. 回收候选/日志，重算差异摘要，区分已合入、仅PR、仅本地和未验证。
5. 核对接口、依赖和证据是否仍有效；按对应阶段继续，不盲重开已完成包。
6. 更新交接，选择下一依赖满足的正式ready任务。

取消先停止写入并确认进程组/锁已回收，再转交新执行者。不能因超时就假设旧进程消失；无法证明终止时隔离原目录和范围。取消不是done，依赖者保持阻断或经规划替换。

## 7. 失败和停止条件

| 信号 | 主控动作 | 继续条件 |
| --- | --- | --- |
| 明确代码/契约失败 | 保留反例，修本包或新规划，不重试到绿 | 原断言通过且新候选完整验收 |
| 同执行者连续两次不合格 | 主控接管/重新切薄/换合格执行者，保留失败 | 新执行者使用相同合法范围和重新验证 |
| 鉴权失败/额度不足 | 停止该渠道，不盲重试/购买/未知付费回退 | 已授权渠道实际可用；不影响任务继续调度 |
| 短暂网络/平台超时 | 合理重试一次，保留实际限制 | 有真实结果；仍未知则记未验证 |
| BASE/接口/共享文件变化 | 停派依赖包，评估影响和重验 | 新基线与契约一致、旧证据已失效处理 |
| 迁移分叉/历史金额差异 | 停止受影响集成，保留原账/迁移 | 主控串行解决、原金额逐分比对、独立复核 |
| 越权、重复账、金额不守恒、数据外发或恢复失败 | 停止相关写路径和扩大影响，保全证据 | 缺陷修复及反例/恢复实证通过；不得直接改库凑数 |
| 真实客户/证书/目标环境缺失 | 完成可独立研发与演练，列明确外部验收条件 | 实际获得合法环境/客户证据，不能自签通过 |

未受影响的独立包可继续；被阻断的工作和最终目标不能写成完成。用户明确暂停则停止派遣、取消/回收并交接；不以“长程目标”覆盖后续暂停指令。

## 8. 资源与沟通

每包设定预计尝试/时间/日志范围，按实际完成周期调整；不凭模型名做能力承诺。审阅、PG环境和迁移成为瓶颈时优先清空集成队列。定期汇报已验收需求、当前关键路径、阻断及所需业务判断；用户无需批准每次常规修复，但应能看到真实剩余工作。

本轮不创建定时器、常驻服务或自动唤醒；若未来用户要求关闭客户端后继续，需要另行明确执行载体和权限，不把前台会话描述成后台服务。
