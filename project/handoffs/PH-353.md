## 设计裁决与偏差

1. **收据写入顺序**：append-only 收据需要 `result_refs`，因此在同一 `transaction.atomic` 内先调用 `core.imports.apply_rows`，成功后再创建 committed 收据；任一步异常仍整批回滚。与契约 §8“先建 pending 收据再更新”的文字顺序不同，但不削弱零半笔语义。
2. **冲突消解**：按任务给定的单表字段实现“未消解 → accept/reject/merge”单向迁移；已消解行不可再改、不可删除，原冲突行保留；未引入独立 resolution 历史表（任务未授权）。
3. **逐行期间绑定**：commit 与 dry_run 在 owner 服务前按 kind 校验业务日期月份 == period（time=work_date、expense=occurred_on、plan=due_date），跨期行以 `row_date_invalid` 拒绝且零写。
4. **future_date**：提交层在预检前拒绝未来 `precheck_as_of_date`（契约 issue_code 注册表）；同月约束仍由 PH-354 预检拒绝，并映射为 `precheck_stale`。
4. **HTTP 路由拆分**：提交页 history_read（auditor 只读、模块停用仍可读历史）与提交写入 business_write 分开，沿用 PH-274 的运行时方法语义。
5. **预览零审计**：`persist_preview` 不写 audit/事件，避免预览阶段产生规范事件；提交收据与 owner 服务审计承担追溯。
6. 未新增 canonical 实体/topic/command；不改 `core/imports.py`。
7. **dry_run 范围**：dry_run 执行预览/预检/冲突/逐行期间校验，但不执行 owner 行校验（apply_rows）；`would_commit=true` 仅表示该阶段通过，最终 owner 拒绝在真实提交时返回 `owner_validation_failed`。
8. **冲突消解并发**：resolve_conflict 未加公司锁/select_for_update；并发消解为后续片加固项，当前单维护者演练不涉及并发消解。
9. **持久预览 HTTP 入口**：本片只提供服务层 `persist_preview` 与提交页；预览持久化 HTTP 上传入口留待后续片（当前预览上传仍走 PH-274 只读 ephemeral 预览）。
