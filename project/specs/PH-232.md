# PH-232 · 核销首片：已过账现金对到期/质保未清项的部分核销与撤核（无预付抵扣）

## 开工资格、价值与范围

PH-231 规划候选；拟依赖 PH-224、PH-228、PH-230（均 done）。须规划 PR 正常合入可信 BASE、依赖 done 且任务 ready 后才可实现，本文不是开工许可。承接 PH-170 第 1 片：把 PH-230 的已过账现金与 PH-224 的 active OpenItem 核销，支持部分核销、上限=双方剩余、撤核（反向记录），使“应收未清→收款核销→剩余/结清”闭环；UAT-14-S01 关键路径（S02 属关期/成本片，不在本片）。**不做预收/预付抵扣（Offset）、退款/银行退回、手续费、内部转账、批量核销、现金账/账本/收入/成本/会计事件**；不解除 PH-170/171 proposed。

## 行为

- 本片不对外暴露 canonical settlement.clearance.create/reverse 命令通道（契约 x-exposure=internal_cash_orchestration_only），仅私有服务承载；不得另建公开写入口。

- **核销创建**：owner/finance 选择同组织、同往来方、direction=in 的 **posted** CashTransaction 与 active、direction=receivable 的 OpenItem；cleared_cents 为正整数，≤ min(现金未核销余额, 未清项剩余)；occurred_on 必须等于现金 transaction_date，非未来、> org.locked_through、期间未关闭；同 token 重放原结果、改输入冲突；一个 (cash, open item) 可有多次部分核销，但累计不得超双方余额。
- **规范事件**：每次创建恰一条 `settlement.cleared.v1`（source=clearance ref v1、payload changed_refs=[clearance ref]、posting_event_refs=[]）；source=clearance ref 版本为创建后的 version。
- **撤核**：仅对 active clearance；采用“原记录单字段状态更新”：仅允许 status active→reversed（金额/引用/date 不变，其余字段 append-only，DB 触发器只放行 status 字段），余额=Σ(active cleared)；不新增反向记录。恰一条 `settlement.clearance_reversed.v1`（source=clearance ref、changed_refs=[clearance ref]）；原因必填（audit/receipt）；同一原记录只能被反向一次；已反向的不能再次反向；撤核后双方余额恢复。
- **余额口径**：现金未核销余额 = posted gross − Σ(active cleared)；未清项剩余 = gross − Σ(active cleared)；不得为负；UI/账龄展示 cleared/remaining。余额/可用证明仅服务端派生（等价 server-only FundingAvailabilityProof），任何调用方提供的余额/证明一律拒绝。
- **对账/只读**：OpenItem 详情/账龄显示 cleared/remaining 与核销历史；clearance 列表按项目/现金/未清项；PM 只读其管理项目；auditor 只读；member 拒绝。
- 明确不做：AccountingEvent/LedgerPosting/LedgerEntry、收入/成本/应收/应付变动、Offset/预付抵扣、退款、手续费、内部转账、批量、导入、期初、AgingCase 写。

## 模型与字段

- `Clearance`（settlement 插件新增）：org、open_item FK(related_name='clearances')、cash_transaction_id UUID（无跨 owner FK；经 cash 具名只读接口校验）、cash_transaction_ref JSON、cleared_cents（>0 ≤1e12）、occurred_on、status(active/reversed)、reverses FK(self, null, related_name='reversals')、reason(Text null)、version、created_by、created_at、receipt FK? 用 CashReceipt? 本插件自建 `ClearanceReceipt`(org, request_token 唯一, action, input_digest, result, created_by, created_at)。
- 约束：cleared_cents>0；occurred_on 非空；status∈{active,reversed}；仅 active→reversed 单字段更新被触发器放行，其余字段不可改、不可删；无 reverses 字段/无反向记录。
- 迁移按实际叶节点生成 settlement 0003（root 单写，不抢号/不改已应用迁移）；不改已应用迁移。

## 服务

- `create_clearance(member, *, open_item_id, cash_transaction_id, cleared_cents, occurred_on=None, request_token, dry_run=True)`：公司锁；fresh 重读角色/项目/OpenItem/Cash（经 cash 具名接口）/期间；校验同 org、同往来方（OpenItem.counterparty_id 与 cash counterparty_id 一致；未识别 payee 拒绝）、cash posted 且 direction=in、OpenItem active 且 receivable、amount/limits、期间/锁账/未来日；条件插入（无版本竞争；以唯一 token + 余额复核）；写 generic audit `settlement.clearance.created`、canonical 事件、receipt；dry_run 零副作用。
- `reverse_clearance(member, clearance_id, *, reason, request_token, expected_version, dry_run=True)`：仅 active；同 org/项目权限；公司锁内 fresh 复核仍 active；条件更新 status active→reversed（仅此字段）；写 audit `settlement.clearance.reversed`、canonical 事件、receipt；重复/并发反向仅一胜。
- `clearance_snapshot/list`、`open_item_balances(member, open_item_id)`：只读投影（owner/finance/auditor；PM 项目范围）。
- cash 侧新增具名只读 `posted_cash_for_clearance(member, transaction_ref)`（root 单写）：返回 posted 现金必要事实与**有效往来方**（优先 transaction.counterparty_id；否则取该流水最新未被反向的 identify CashPartyMatch.identified_payee，并返回 match ref/version 供审计；两者皆无=未识别），未 posted/跨 org 拒绝。核销匹配用有效往来方与 OpenItem.counterparty_id；匹配已被反向则视为未识别拒绝。
- 不写 SourceConsumption；余额由 Clearance 聚合派生，不另建可编辑余额。

## 权限与拒绝

- 写：owner/finance（项目可见）；读：owner/finance/auditor、PM 仅管理项目；member 拒绝。cash 模块停用时核销写入口与 cash 只读接口拒绝。
- 拒绝：未 posted/草稿现金、direction 不符、跨 org/项目/往来方、OpenItem 非 active/非应收、金额≤0/超双方剩余/bool/float/超 1e12、未来日/locked_through/关期、重复 token 改输入、撤核非 active/重复反向/并发、撤权、停用模块写拒绝。
- 所有拒绝零半笔：Clearance/ClearanceReceipt/DomainEvent/AuditEvent/（无）AccountingEvent/Ledger/Settlement/OpenItem/SourceConsumption 计数不变（generic audit 与其非 canonical 事件除外）。
