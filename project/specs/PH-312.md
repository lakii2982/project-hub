# 实现前置决策与 PH-322 可执行切片冻结（PH-312，2026-10-31，docs-only）

> 本正文是本片唯一交付物：按 ADR 0016/0017 在实现前完成映射取舍、迁移/回填/约束计划、命令边界、只读核对、更正路径、通知联动前置，并给出可直接施工的 PH-322 实现切片 spec。
> BASE：`2659317`。本片白名单**不含代码/迁移/schema/docs/adr**，故本片不落地任何 schema/迁移骨架；下文是 PH-322 的施工契约，PH-322 白名单需由规划槽按其 spec 扩充（见 §9）。
> 本片不写期间/项目状态、不写账本/业务事实、不建命令/路由；不抢迁移号。

## 1. 决策摘要

| 对象 | 决策 | 理由 |
|---|---|---|
| 期间关期 `closing/reopened` | **方案 B：append-only `PeriodCloseRun`（delivery 插件）** | `AccountingPeriod.status` 仅 `active/posted` 且有 CheckConstraint `active↔closed_through IS NULL`、`posted↔closed_through NOT NULL`；既有 owner 服务（cash/settlement/revenue/time/contracts）依赖该边界拒写。扩展 status（方案 A）会同时破坏既有约束与全部 owner 期间校验语义，风险远高。B 让 `closing/reopened` 只存在于追加 run，关期提交仍落到既有 `posted/closed_through`，既有写拒绝边界不变；append-only run 保留关期/重开历史。 |
| 项目结项 `closing/reopened` | **方案 B：append-only `ProjectClose`（delivery 插件）** | ADR 0017 推荐；`Project.stage` 枚举无 `closing/reopened`，且 `cancelled` 与 `closed` 是独立终态。B 不污染 stage 枚举；结项提交仍写既有 `stage='closed'`，既有 `check_open()`/owner 校验不变；重开恢复关闭前 stage。 |
| 落点 | 两个新模型都放 **delivery 插件**（`pmo_plugins/delivery/models.py` + 迁移 `0005`），都引用 core 的 `AccountingPeriod`/`Project`；不改 core schema/迁移 | delivery 已有关期/结项核对与工作台只读来源；core 仅作为期间/项目 current 状态所有者被更新既有行（不新增 core 字段/表），避免 core 迁移与他片抢号；命令/读模型也在 delivery。 |
| 迁移/回填 | 仅新增两张 append-only 表 + 约束 + vendor-aware append-only guard；**无数据回填**（既有 active/posted、stage 原样即映射） | B 不改变既有行形状；既有历史关期/结项在 run 缺失时按 current 状态映射并标记 `historical_close_without_run`（只读 warning），不伪造 run、不回改写历史。 |

## 2. 方案 A 为何不采用（记录取舍证据）

- 方案 A（扩展 `AccountingPeriod.status` 允许 `closing/reopened`）需要：新迁移放宽/替换 `labor_period_closed_date` CheckConstraint；更新所有 owner 的期间判断（目前多处精确判断 `status != 'active' or closed_through is not None`，见 `core/labor_accounting.py`、`core/revenue_accounting.py`、cash/settlement/time 服务）；同时仍要另建 append-only 结论表才能满足 ADR 的“关期结论只追加”。这既改既有 schema/全部写拒绝语义，又不能省掉 run 表，收益为负。
- 方案 A（扩展 `Project.stage`）需要：放宽 stage 约束/迁移、更新项目阶段流转与 `previous_stage` 语义、并同步所有 owner 项目状态判断；同样仍需 append-only 结论表。ADR 0017 也明确推荐 B。
- 结论：**A 仅作为历史备选记录，不实现**；若未来确需 durable `closing` 可观察状态，再单独立项评估，不在 PH-322 内改。

| `closed_through` | DateField(null=True) | close 的 closing/closed 行为该期间月末；reopen 行为写入前旧 closed_through（审计留痕） |
| `blockers` | JSONField(default=list) | 预检 blocker refs 快照（只读、不可再解释） |

| `precheck_digest` | CharField(64) | 预检结果规范化 JSON 的 sha256，用于幂等/证据 |

| `actor` | FK core.Membership PROTECT | 执行人（owner/finance） |
| `request_token` | UUIDField(null=True) | 命令幂等 token（仅每命令首行写；org 内唯一由 DeliveryReceipt 保证） |
| `created_at` | DateTimeField(auto_now_add) | |

约束（迁移中建立）：
- `UniqueConstraint(organization, period, sequence)`；
- `UniqueConstraint(organization, request_token)`（同 org 同 token 只允许一命令；close 的两行共用同一 token 会冲突，故 **receipt 用 DeliveryReceipt，run 的 request_token 仅存首行/重开行**——冻结：closing 行写 token，closed 行写同一 token 会违反唯一，故 closed 行 token 用 `None`（字段 null=True）或另加 `command_token` 不唯一；最终冻结：`request_token` **null=True**，仅每个命令的第一行（closing 或 reopened）写 token；closed 行 null；唯一约束对 null 不生效，服务层用 DeliveryReceipt 做幂等）；
- `CheckConstraint(action in ('close','reopen'))`；
- `CheckConstraint(state in ('closing','closed','reopened'))`；
- `CheckConstraint((action='close' AND state IN ('closing','closed')) OR (action='reopen' AND state='reopened'))`；
- `CheckConstraint(state != 'closed' OR closed_through IS NOT NULL)`；
- 追加守护：SQLite `BEFORE UPDATE/DELETE` trigger + PG `BEFORE UPDATE OR DELETE` function/trigger 拒绝改/删（vendor-aware，名字按实际表）；模型 `save` 仅允许新增、`delete` 拒绝。
- 索引：`(organization, period, sequence)` 唯一；`(organization, accounting_period, created_at)` 查询索引。

### 3.1 期间契约状态派生（只读）

- `latest = 同 org+period `sequence` 最大的 run`。
- 无 run：若 `AccountingPeriod.status='active'` → `open`；若 `posted` → `closed`（历史关期），附 `historical_close_without_run=true` warning，**不伪造 run**。
- latest.state='closed' → `closed`；latest.state='reopened' → `open`（重开后），并保留历史 closed run；latest.state='closing' 只存在于关期事务内，提交后不可见；读模型若读到 dangling closing（异常）→ `closing` + `dangling_closing` issue，不当作 closed。
- `open`/`closed` 的写边界仍由既有 `AccountingPeriod.status/closed_through` 决定：**run 不替代 owner 期间校验**；`closing` 只在命令持有公司锁的同一事务内存在，提交前不对外可见，故既有 owner 不需要新增 `closing` 分支（这是 B 的关键收益）。
- **关于 ADR 的 `closing` 可观察状态**：本前置决策把 `closing` 落地为**事务内阶段**而非持久可观察状态；ADR 的“预检通过、关期进行中仅关期命令可写”由公司锁 + 原子事务保证。这是 B 下唯一不触碰既有 owner 校验的实现解释；若后续产品要求 durable `closing` 可查询，须另立规划（不在 PH-322 内改），不得把事务内阶段伪称已持久化。
- 关期提交：同一 `transaction.atomic` + `lock_company` 内：预检→写 closing run→更新 `AccountingPeriod.status='posted', closed_through=period_end, version=version+1`→写 closed run→写审计/收据。任一步失败回滚，无半笔、无 dangling closing。
- 重开提交：同一事务：校验 latest closed、reason 非空、收据→更新 `AccountingPeriod.status='active', closed_through=None, version+1`→写 reopened run→审计/收据。历史 closed run 不改。

### 3.2 回填/迁移/回滚

- 迁移只创建表/约束/守护，不 backfill；既有 ledger/period 事实一律不改。
- 回滚：`migrate delivery 0004` 删表即可；无 core 迁移、无数据迁移。历史 active/posted 行仍可用。
- 不回填、不重算既有历史；`historical_close_without_run` 只读提示由读模型动态派生。

### 4.1 项目契约状态派生

- latest run：closed→`closed`；reopened→`active`（恢复 from_stage）；无 run 时按 `Project.stage ∈ {closed,cancelled}` 映射：closed→`closed`（`historical_close_without_run` warning），cancelled→`cancelled`（非结项），其余→`active`。
- `closing` 仅在结项事务内存在，提交后不可见；dangling closing 读为异常 issue，不当作 closed。
- 结项提交（同一事务+公司锁）：预检→写 closing run→更新 `Project.stage='closed', previous_stage=from_stage, version+1`→写 closed run→审计/收据。
- 重开提交：校验 latest closed、reason、receipt→恢复 `Project.stage=最近 closed.from_stage`（若该值非法/为 closed 则拒绝），`previous_stage='closed'`，`version+1`→写 reopened run→审计/收据。
- 结项后 owner 写拒绝仍依赖既有 `Project.stage closed` + 各 owner `check_open`/项目范围校验；PH-322 必须补 verify_integrity/测试核对各 owner 不因阶段枚举共存而漏写（见 §8 测试）。

## 5. 命令边界（PH-322 服务契约，冻结）

文件：`pmo_plugins/delivery/close_services.py`（新增；PH-322 白名单已有该文件，但需扩 models/migrations，见 §9）。

```text
period_close_precheck(member, period, *, as_of=None) -> dict
reopen_period_precheck(member, period, *, as_of=None) -> dict
close_period(member, period, *, request_token, dry_run=True, expected_version, reason='') -> dict

```

- 权限：owner/finance 可执行/可 dry_run；auditor 只读（precheck 可读，执行拒绝）；pm 仅管理项目摘要（precheck 摘要，执行拒绝）；member 拒绝；未登录 403；模块停用后历史只读可读，写拒绝。
- `dry_run=True` 默认：只读预检 + 计划摘要，**零写**（无 run/收据/审计/period/project 更新）；`dry_run=False` 才执行。
- 幂等：`request_token` + input digest（period/project、expected_version、reason、dry_run、预检 digest、操作者）；同 org+token 同输入返回首次 result（重放不写）；同 token 改输入 `idempotency_conflict`；同期间/项目并发由 `lock_company` 串行，后到者因 expected_version/当前状态不符 `period_already_closed`/`project_already_closed`。
- `expected_version` 必填：匹配 `AccountingPeriod.version`/`Project.version`，不符 `stale_version`，零写。
- 审计：执行时 `core.audit(member, 'plugin.delivery.period_closed'/'plugin.delivery.period_reopened'/'plugin.delivery.project_closed'/'plugin.delivery.project_reopened', run, payload)`，使用 `plugin.` 前缀避免新增 canonical DomainEvent topic；payload 含 run ref、period/project、summary、receipt id。dry_run 不写审计。
- 命令不写账本/收入/成本/现金/未清，不自动修正、不自动审批、不推送外部；关期/结项只更新 current 状态行 + append run + 审计/收据。

- 输入 `as_of`/`period` 只读过滤；缺失能力 `null + missing`，不显示 0。

  - 收入配对：`management_revenue.pairing_read_services.revenue_pairing_snapshot/issues`（PH-284）；

  - 现金：`cash.bank_balance_services.bank_account_balance_snapshot/bank_account_issues`（PH-288）；

- 期间预检 blockers（冻结 issue_code）：`unapproved_documents`, `timesheet_pending`, `cash_unposted`, `settlement_coverage_issue`, `revenue_pairing_issue`, `fee_pairing_issue`, `contract_termination_pending`, `import_preview_conflict`, `future_dated_fact`, `period_already_closed`；warnings：`historical_close_without_run`, `forecast_gap`, `open_item_warning`, `import_preview_warning`。

- 预检结果整体 `precheck_digest = sha256(canonical_json(...))`，写入 run/收据；执行时重算，若与 dry_run 计划不同（事实变化）→ `precheck_changed` 拒绝，零写（要求重新预检）。
- precheck 失败仍返回 blockers（read-only），不抛半笔；页面 200 + 区块；越权/非法参数 400/403。

## 7. 更正路径（冻结）

- 关期/结项后发现的错误：只允许 (a) 原 owner 的既有负值冲销/红冲/撤核/撤转/撤分类（保留原始来源），或 (b) 明确重开命令（append-only `reopened` run），在重开后的开放期间追加更正；**禁止**直接改历史行、删除 run、改 AccountingPeriod/Project 历史结论。
- 重开本身不修正任何业务事实，只恢复可写状态；更正仍走原 owner 命令并留 source refs。
- 已关期/结项期间对 owner 写请求由 owner 既有校验拒绝（`check_period`/`closed_through`/`check_open`/project stage）；关期/结项服务不代理业务写、不自动生成调整分录。
- 任何“结项后自动补记/重算”不在本契约；需另立规划。

## 8. 通知联动前置（只读 reminder refs）

- 当前无通知中心实现（PH-301 未交付）；本片只冻结**只读提醒 ref** 形状，不建立通知写侧、不自动审批/支付/关期/结项。
- 每个 blocker/warning 附：

  1. run sequence 从 1 连续、state/action 组合合法、closed 行 closed_through 非空；
  2. latest run 状态与 AccountingPeriod.status/closed_through 一致（closed→posted、reopened→active；无 run 时历史映射 consistency）；
  3. 无 dangling closing：成功关期会在同一事务追加 `closing`（sequence=n）+ `closed`（sequence=n+1）两条 append-only 历史行，因此提交后**允许成对的 closing 行存在**；`dangling` 仅指某 closing 行（同 org+period/project）缺少紧邻的下一条 `closed` 行且不是 latest 状态，或 latest run 为 `closing`（事务外可见即 corruption）。verifier 必须校验 closing→closed 成对与 sequence 连续，而不是禁止所有 closing 行。
  4. ProjectClose latest 与 Project.stage（closed/恢复 from_stage）一致；cancelled 不得有 close run；reopen from_stage 合法；
  5. 收据/结果引用存在、append-only (DB guard probe tests)。
- 出错 envelope 与既有 verifier 一致（errors list）；探针测试 vendor-aware。
