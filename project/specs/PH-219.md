## owner、数据与契约

- delivery App 唯一写 Acceptance、AcceptanceCoverage、CustomerConfirmationEvidence、AcceptanceReversal 与业务幂等 receipt；复用 core.Milestone，不建第二节点表。
- management_revenue App 唯一写 RevenueRecognition、RevenueAdjustment 与 receipt；收入净额只由原确认金额加 signed adjustment 汇总，不建可编辑余额。
- contracts owner 增加只读 `approved_line_snapshot(member,line_ref,as_of)`：授权同组织项目，检查 active 合同及唯一有效 approved ContractVersion、实际 ContractLine 与唯一 approved Selection，日期不早于 effective_on；返回不可变净税总额、节点配置、真实 policy_version/批准版本/审计与冻结摘要。不从 Project.contract_cents 推算。
- owner 必须核验 `version.submitted_digest == _frozen_digest(version) == approval_audit.payload.submitted_digest`；line_no/net/tax/gross 对应冻结 draft 候选，Selection 去掉服务器补的 currency/confirmed_by_customer_required/policy_ref 后等于原候选；policyRef、批准者、日期、audit 均真实关联。未知、多 approved、篡改配置/明细拒绝。保持合同批准写路径和旧迁移不变。
- 客户依据是 delivery 自有不可变人工登记：客户联系人（同合同客户）、确认渠道、依据编号、确认内容、客户确认日期、创建人和服务器 SHA-256。文本必填、长度受表单限制（联系人100、渠道100、编号200、内容2000）；客户端不能提供 hash、创建人。`EvidenceRef {evidence_id,sha256,kind:customer_confirmation}` 指真实登记 PK，详情明确显示「客户确认依据登记／核对」，不声称上传了附件、外部客户签署或内部批准证明了外部事实。先登记后保存草稿；默认 dry_run 不落登记。
- Acceptance 草稿输入严格沿 `write-dtos.schema.json#/$defs/AcceptanceDraft` 的 project_id、contract_line_ref、confirmed_on、evidence、milestone_coverages；组织/actor/审批者/金额不可写。coverage 逐项 milestone_id/from_basis_points/to_basis_points，数组 1..1000。每条节点只能来自所选批准 line，配置金额之和等于 line.net_cents。
- confirmed Acceptance 持久化真实 line/版本/Selection/原配置/依据 hash/每段金额快照与创建、提交、确认 actor，批准后不改原事实。Reversal 追加一对一指原 Acceptance、reason、执行人、创建时间；status 投影为 reversed。原快照与 FK 永久可解析。
- RevenueRecognition 私有字段含真实 Acceptance FK、contract_line_ref、原 policy/configuration、algorithm_version、净额、occurred_on、actor、core AccountingEvent FK；公共投影只输出 canonical 字段。RevenueAdjustment 含唯一 reverses Recognition / 原 event、负原金额、reason、原日期期间、真实创建时间和 actor；不提供任意调整金额。

## 状态、金额与日期

Acceptance `draft → submitted（内部审批流程）→ confirmed`，退回可编辑草稿，拒绝保留审批历史；草稿/待审/withdrawn仅输出私有工作流UI读模型，不输出缺真实confirmed_by的完整canonical Acceptance；确认才输出confirmed规范实体；confirmed 仅能追加 reversal 成为 reversed。重复提交、过期 expected_version、未知决策拒绝。确认本身不修改 Milestone.completed，不写收入/现金。确认日期由记录人明确登记，须等于登记的客户确认业务日期、`effective_on <= confirmed_on <= Asia/Shanghai today`；服务器确定审批人，不能自动今天替代客户日期。

对节点批准金额 M，覆盖 `[from,to)` 金额为 `HALF_UP(Decimal(M)*to/10000) - HALF_UP(Decimal(M)*from/10000)`，`0 <= from < to <= 10000`。101分连续 0..3333、3333..6667、6667..10000 必为 34/33/34；允许部分和缺口。active confirmed 覆盖按 **org + project + 真实 milestone ID** 跨所有 line、合同、版本检查不重叠，草稿内部亦检查。PH-214 同版本节点去重不保证跨合同节点唯一，本片不改批准行为；不同履约须客户另建真实节点，不能换 line/key 绕过。同 line 稳定 ID 的累计收入不得超过批准净额；零额覆盖同样占用。

RevenueRecognition 只接受 independently confirmed、未逆转且未消费 Acceptance，精确取 accepted_net_cents，无手填金额、权重、实际分钟猜价。直接生成 posted 不新增第三审批层。来源唯一键为 org + consumer management_revenue + 原 Acceptance ID + 固定 coverage 用途，排除 version/key/channel；source claim 持久保留。零元也检查唯一 active Recognition 和来源终态，不能仅以 sum(amount)=0 判断可重用。

`occurred_on = Acceptance.confirmed_on`，posting_period 为该月，客户端不能改。使用现 AccountingPeriod，收入与 LaborCutover/costing 启用独立；持有公司锁且来源已独立确认时可建立其 active 月份，只做具名收入操作，不建通用期间框架。org.locked_through 与 period.closed 双重拒绝。所有整数金额绝对值 <= 10^12 分，Decimal/ROUND_HALF_UP，拒 bool/float；累计用精确整数。

## 会计桥、纠错与完整性

具名 `core/revenue_accounting.py` 接入现有 bridge；AccountingEvent.source 指真实 recognition/adjustment，claim.source 指真实 Acceptance，consumer=management_revenue，claim_effect_cents 为正原额/负原额；收入 event.labor_origin_ref=None。core/models.py 唯一窄改为此 JSONField nullable，新迁移保留旧值；劳动服务仍要求真实工资池，不填 {}、不造 salarypool、不添 income_origin。

收入事实与冲销仅入 management_revenue owner，桥不再记一份余额，不写 LedgerPosting 或 LedgerEntry，不伪装成本/cash_in。verify_integrity 按 source.namespace 具名验证 income FK/同组织项目/原来源/金额/claim effect/一对一 reversal、无 cost/cash postings；保留原劳动分支全部不变，包括劳动来源必须存在。

纠错先由 owner/finance 显式完整反收入，再由另一 owner/finance 反验收；禁止自动级联。RevenueAdjustment=-原 Recognition 金额且唯一 reverses，追加负 claim effect 和逆向 event，复制原 occurred_on/posting_period，created_at 为真实操作时间；原期锁定拒绝，未来开放期差额留 PH-166。零元仍追加唯一冲销与终态。原 Acceptance 一旦产出被冲收入即不能再次认收入、更换 key 无效；随后反验收释放覆盖，新的正确 Acceptance 是新来源，可重新确认。若重用已反验收的实际节点覆盖，必须显式传 replaces_acceptance_ref，指同 org/project/line 且终态 reversed、原收入全反及无未清财务依赖的原 Acceptance；private FK 保存替代链，原记录不改。选了替代来源即完整核验，即使新覆盖不相同也不放松；不重用旧覆盖可不传。修正使用新的真实客户依据和独立审批，不能冒用原批准。验收有未冲收入时不可逆转。历史纠错读取原批准版本/快照与原 source，不因当前客户资料停用而无法纠错，但权限、模块、原期锁定仍重查；禁止删除或重写旧事实。

## 具名账务桥的事务顺序

收入服务在同一外层atomic中先创建私有unposted候选Recognition（status=draft、core_event=null、真实Acceptance FK、服务端原价、version1），此候选不是客户端可维护的另一收入草稿；core具名helper核实际候选行和独立已批验收，建立唯一claim及实际AccountingEvent，返回event后收入owner一次定稿为posted并关联event。Adjustment同样先有真实候选事实行后建反事件，金额只取负原分；任何失败回滚全部，不准提交孤立event或无event的posted收入。posted Recognition/Adjustment全部字段由DB触发器禁止UPDATE/DELETE；有效已反状态由追加Adjustment派生，原posted事实和版本永久保留。UI的有效状态不是可改原账余额。完整性检查必须拒posted缺event或event无真实收入/调整，并验证claim首event与反向关系。core不写收入owner表，income owner不写cost/cash行。
